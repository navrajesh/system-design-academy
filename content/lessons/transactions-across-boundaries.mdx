<BigPicture>

A transaction turns several state changes into one decision: commit all or expose none. Inside one database, ACID transactions, locks, MVCC, and constraints can enforce that decision. Across a database, broker, payment provider, or another service, there is no automatic shared rollback. The architecture must either coordinate participants or model the workflow as durable state with retries and compensation.

TokenX can move value between two wallets in one database transaction: lock or serialize the accounts, insert balanced ledger entries, update materialized balances, record the idempotency result, and append an outbox event. The broker publish happens later. This preserves financial invariants without pretending the database and Kafka share one atomic commit.

</BigPicture>

<UnderTheHood>

### Isolation is about allowed histories

Common anomalies include lost updates, dirty reads, non-repeatable reads, phantoms, and write skew. MVCC gives readers snapshots, but “snapshot isolation” can still allow two transactions to read the same valid state and make disjoint writes that jointly violate an invariant. Serializable isolation, an explicit lock, a uniqueness or exclusion constraint, or an atomic compare-and-set must protect the invariant—not a hopeful read followed by write.

For TokenX, a conditional debit such as `UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?` can atomically prevent a negative balance for one row. A transfer across two rows also needs deterministic lock order or serializable retry to avoid deadlocks and write skew. Deadlock aborts are normal control flow; retry the entire transaction with the same idempotency key.

The relay can crash after Kafka accepts the event but before the outbox row is marked published, so it must publish again. Delivery is at least once. Consumer offset commits alone do not make an external database update replay-safe: the consumer can crash after the database commit but before committing the offset. The inbox uniqueness constraint closes that ambiguity for the database side effect.

At 2,000 transfers/s, one event per transfer, and a 15-minute broker outage, the outbox accumulates `2,000 × 900 = 1.8 million` rows. At 700 bytes per row that is about 1.26 GB before indexes. If the relay recovers at 8,000 events/s while 2,000/s continue arriving, net drain is 6,000/s and ideal catch-up is 300 seconds. Size indexes, autovacuum, and alerting for the outage case, not only steady state.

### When one transaction is impossible

Two-phase commit (2PC) asks participants to prepare, then commit. It can provide atomic agreement for compatible resources, but the coordinator and prepared locks create availability and operational risks. Across independently deployed services or external providers, a saga is often more appropriate: persist workflow state, execute idempotent steps, and compensate completed steps when later steps fail.

Compensation is not time travel. Refunding a card may incur fees; releasing inventory may fail; a delivered notification cannot be unsent. Reserve scarce resources before confirmation, give every step an idempotency key, use deadlines, and define manual-resolution states for exhausted retries.

Cross-shard TokenX is that saga with exclusive terminals, not a cache TTL. The invariant is conservation of the transfer amount: it is reserved on the source, credited on the destination, or returned to the source—never both spent and credited. Authoritative state lives on each shard's ledger. The coordinator's RPC timeouts are not ledger facts.

Shard B keys one durable row by stable `transfer_id`: `ABSENT → CREDITED | CANCELLED`. Credit and cancel race in one serializable destination transaction. The winner is terminal. Duplicates return the committed outcome. A delayed credit after `CANCELLED` is rejected. A delayed cancel after `CREDITED` cannot reverse the credit. Cancel of an unused id still writes a `CANCELLED` tombstone; otherwise a late credit still commits. This lesson does not use a provisional spendable destination credit.

Shard A inserts the reservation uniquely on `transfer_id` (unique constraint or insert-if-absent) in one atomic transaction. Concurrent reserve attempts for the same id must not create two `RESERVED` rows. After that insert, `RESERVED → FINALIZED | RELEASED` is an exclusive fork: a conditional update from `RESERVED` can take only one branch. On timeout the coordinator persists `UNRESOLVED` and queries B. `CREDITED` drives finalize. `CANCELLED` drives release. `ABSENT` or an unknown query keeps `UNRESOLVED`. Never treat a lost response as cancellation.

<MentalModel>

One database transaction is a sealed envelope: either the whole instruction becomes official or none does. A distributed workflow is a checklist mailed between offices. Each office stamps what it completed, recognizes duplicate mail, and knows the compensating procedure—but cannot erase real-world effects.

Retain: shrink the invariant boundary, commit state and intent together, make every boundary replay-safe, and model compensation as a business action.

</MentalModel>

<RealExamples>

**TokenX same-shard transfer.** Co-locate accounts that transact together when possible. Use balanced immutable entries and a unique idempotency key. A derived history consumer may process an event twice, but its inbox prevents duplicate rows. It never changes the authoritative balance.

**TokenX cross-shard transfer.** Use exclusive terminals: B `ABSENT → CREDITED | CANCELLED` and A unique `RESERVED` insert, then `RESERVED → FINALIZED | RELEASED`. The `RESERVED` insert is atomic and unique on `transfer_id`. Later terminals still require a conditional update from `RESERVED`. Timeout is `UNRESOLVED`: query B's committed row. Finalize only on `CREDITED`; release only on a durable `CANCELLED` tombstone; retry while `ABSENT` or unknown. Coordinator epochs fence stale workers but do not replace the tombstone. If strict instantaneous conservation across shards is mandatory, distributed consensus or redesign may be required.

**Ad Click billing.** Click aggregation is replayable, but invoicing an advertiser is an external effect. Close a versioned billing period, create one invoice command per account under a unique key, and record provider request and result. Replaying raw clicks may produce a corrected invoice version; it must not charge the card twice.

<InterviewTraps>

1. **“The database is ACID, so the workflow is atomic.”** List every resource boundary, including broker publish, emails, payment providers, caches, and search indexes.
2. **“Read committed prevents double spend.”** It prevents dirty reads, not every lost update or write skew. Show the constraint, lock, or serializable transaction.
3. **“Kafka exactly-once handles the database.”** Kafka can atomically coordinate Kafka records and offsets in supported flows; external database writes need inbox/idempotency or a connector with proven semantics.
4. **“A saga rolls everything back.”** Compensation can be lossy or impossible. Name irreversible steps and manual resolution.
5. **“Retry on timeout.”** A timeout means unknown outcome. Retry with the same identity and query the durable workflow state. For TokenX, do not release a source reservation until B has committed `CANCELLED`.
6. **“2PC guarantees availability.”** Prepared transactions can hold locks while a coordinator is unavailable; discuss recovery tooling and participant support.

Staff+ answers state the invariant first, minimize its atomic scope, then describe every ambiguous crash point.

</InterviewTraps>

<Tradeoffs>

- Serializable transactions simplify reasoning but may abort more under contention; they become inappropriate for a single ultra-hot row without partitioning or sequencing.
- Explicit locks make ordering visible but reduce concurrency and require deadlock discipline.
- Outbox/inbox accepts duplicate transport and operational cleanup in exchange for a local atomic boundary and replay safety.
- 2PC offers atomic agreement for compatible participants but couples availability and operations across them.
- Sagas preserve service autonomy and availability but expose intermediate states and require domain-specific compensation.

</Tradeoffs>

<InterviewAnswer>

“I first state the invariant and place as much of it as possible inside one database transaction. TokenX commits balanced ledger entries, balances, idempotency result, and outbox intent together under an enforceable isolation strategy. A relay publishes at least once; consumers atomically combine an inbox key with their local update, so crashes around offset commits are replay-safe.

When one transaction cannot span the workflow, I choose consciously between 2PC and a saga. Cross-shard TokenX uses exclusive terminals on each ledger: B `CREDITED` or `CANCELLED`, A one unique `RESERVED` insert then `FINALIZED` or `RELEASED`, with `UNRESOLVED` until B's committed `transfer_id` row is known. Related lessons are [relational versus NoSQL](/learn/relational-vs-nosql-selection), [Kafka delivery](/learn/kafka-delivery-and-failure), and [replication](/learn/replication-and-failover).”
