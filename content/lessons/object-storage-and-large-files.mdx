<BigPicture>

Object storage is a durable key-to-bytes service optimized for large immutable blobs, massive namespace scale, and lifecycle tiering. It is not a relational database, shared POSIX filesystem, or transaction coordinator. A production design normally keeps authorization, ownership, state, and business metadata in a database while object storage owns the bytes.

TokenX may store monthly statements, identity evidence, and reconciliation exports. The Ad Click Aggregator may store ad creatives and immutable raw event segments. In both cases, clients should move large bytes directly to object storage through narrowly scoped signed requests while an application service controls which object becomes visible.

</BigPicture>

<UnderTheHood>

### Control plane and data plane

The control API authenticates the user, creates an upload record with an unguessable object key, size limit, content policy, and expiry, then returns short-lived signed part URLs. The client uploads directly. Finalization verifies part checksums, expected total size, object existence, and scanning policy before atomically changing metadata from `UPLOADING` to `AVAILABLE`.

Never treat a user-provided filename as the storage key or authorization boundary. Store it as escaped display metadata. Prefer immutable keys such as `tenant/object-id/version`; replacing content creates a new version, then one metadata transaction changes the active reference.

### Transfer calculation

A 5 GiB export split into 64 MiB parts needs `5 × 1024 / 64 = 80` parts. A 100 Mbit/s uplink carries at most 12.5 MB/s, so the ideal lower bound is about `5,368 MB / 12.5 ≈ 429 seconds`, or 7.2 minutes. Eight-way parallel upload can hide per-request latency and recover individual failures, but it cannot exceed the bottleneck link. Budget retries, encryption, and provider throttling.

Part size is a three-way compromise: small parts improve retry granularity but increase request and metadata overhead; large parts reduce requests but make retries costly; provider part-count limits impose a lower bound for huge objects.

### Reads, integrity, and lifecycle

Range requests support video seeking and partial downloads. A CDN reduces origin requests and user latency, but private objects need signed delivery URLs and cache-key discipline. Store content type from validated bytes, not a trusted client header. Use cryptographic whole-object checksums for integrity; multipart ETags are provider-specific and may not be a content hash.

Lifecycle rules transition immutable versions to colder tiers and eventually expire them. Deleting the database row first can orphan bytes; deleting bytes first can leave a visible broken reference. Use a state machine: mark `DELETING`, revoke access, delete versions, verify, then tombstone metadata. Legal holds and backup retention override ordinary expiry and must be auditable.

<RealExamples>

**TokenX statement export.** A background worker writes a statement to an immutable version, verifies row count and checksum, then updates the statement record. The download API authorizes the wallet owner and returns a short-lived CDN URL. Regeneration creates a new version; audit logs retain which version a customer received.

**Ad creative upload.** The client uploads directly to quarantine. Image and malware validation runs before campaign metadata can reference it. Derivative thumbnails have deterministic keys derived from source version plus transformation version, so retries do not create duplicates.

**Raw click archive.** Stream processors seal hourly segments with schema version, time bounds, record count, and checksum in a manifest. A segment is discoverable only after the manifest commits. Reprocessing reads the manifest, not a bucket listing whose ordering or cross-provider semantics should not be assumed.

<InterviewTraps>

1. **“Store the file in the database.”** Small transactional blobs can be reasonable, but large files inflate WAL, backups, replicas, and buffer caches. Quantify the crossover.
2. **“The signed URL handles security.”** Scope key, method, size, checksum, content rules, tenant, and expiry; authorize again on download.
3. **“ETag is the MD5.”** Multipart and encrypted objects may use different semantics. Request and verify a defined checksum.
4. **“Rename the object atomically.”** Many object stores use copy-plus-delete or lack filesystem rename. Publish by switching a metadata pointer to an immutable key.
5. **“Delete means gone.”** Account for versions, replicas, CDN caches, archives, backups, legal holds, and encryption keys.
6. **“Bytes in the bucket are live.”** Assembled parts are still quarantined while metadata is `UPLOADING`. The CDN must not serve until a conditional control-plane commit marks the exact version `AVAILABLE`.

A staff+ answer names the incomplete states and cleanup owners rather than describing only the happy path.

</InterviewTraps>

<Tradeoffs>

- Direct client upload removes application bandwidth but requires constrained delegation and hostile-input validation.
- Multipart transfer improves resume and parallelism but creates incomplete state and request cost.
- Immutable versioning simplifies caches, audit, and rollback but consumes storage until lifecycle rules expire old versions.
- CDN delivery reduces latency and egress from origin but complicates revocation and cache invalidation.
- Cold tiers reduce storage price but increase retrieval latency and fees; they are inappropriate for data with tight restore objectives unless staged copies exist.

</Tradeoffs>

<InterviewAnswer>

“I separate the data plane from the control plane. Object storage owns immutable bytes; the metadata database owns tenant, authorization, lifecycle state, and the active version. Clients use short-lived, tightly scoped multipart URLs. Finalization verifies size and cryptographic checksum, scans in quarantine, then atomically publishes one exact version.

I calculate part count and link-limited transfer time, design bounded resume plus orphan cleanup, and include versions, CDN caches, backups, and legal holds in deletion. Related lessons are [time-series archives](/learn/time-series-and-append-only-storage), [transactions across boundaries](/learn/transactions-across-boundaries), and [backup and recovery](/learn/backup-restore-and-disaster-recovery).”

</InterviewAnswer>
