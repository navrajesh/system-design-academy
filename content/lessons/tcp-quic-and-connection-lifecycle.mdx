<BigPicture title="A connection is transport state, not a ledger row">

[Networking for system design](/learn/networking-for-system-design) established that TCP preserves byte order **on one connection** and that a timeout is not a rollback. This lesson is the **lifecycle**: handshake cost, TLS 1.3 1-RTT versus 0-RTT replay, congestion and slow start, HTTP/1.1 versus HTTP/2 head-of-line blocking versus QUIC, keepalive, pooling, TIME_WAIT, NAT idle timeouts, and drain versus RST.

The connection table on the client, the load balancer, and the NAT is **derived transport state**. It can be rebuilt by dialing again. TokenX money still commits in the ledger with `(tenant, transfer_id)`. Ad Click billed facts still commit on the log with `click_id`. Reusing a socket is amortization. It is not session affinity correctness, and it is not exactly-once.

</BigPicture>

<UnderTheHood title="Handshake, loss, reuse, then an honest UNKNOWN">

### What you pay before the first byte of POST /debits

TCP handshake is 1 RTT (SYN, SYN-ACK, ACK). TLS 1.3 on a new connection is typically **1-RTT** more after TCP, with session resumption sometimes overlapping. **0-RTT** (early data) sends application bytes in the first client flight using a previous PSK. Those bytes can be **replayed** by a network attacker or a buggy retry. TokenX **must not** put spendable debits in 0-RTT. Ad Click ingest must not put a new `click_id` in 0-RTT unless the log is already idempotent on that id—and even then you still replayed offered load.

Slow start and congestion windows mean a new connection is a worse p99 than a warm one. That is why pools exist. It is also why a pool of idle sockets can hide a dead backend until the first write, which is why [load balancing](/learn/load-balancing-deep-dive) health and idle timeouts must match.

### Head-of-line blocking is not one idea

- **HTTP/1.1:** one request at a time per connection (pipelining is a museum piece). Loss delays that one request. You scale with more connections, which costs RAM, sockets, and slow start.
- **HTTP/2 over TCP:** many streams, one congestion context. A lost TCP packet stalls **all** streams until retransmission. That is **TCP HOL**, not application FIFO.
- **QUIC / HTTP/3:** streams mostly recover independently because loss is per-stream at the QUIC layer. You still share a connection-level congestion window. QUIC is not infinite parallelism and not a TokenX transaction.

<Calculation label="Pool occupancy and TIME_WAIT (illustrative)">

TokenX API: 2,000 req/s, mean service 20 ms, HTTP/1.1 one-request-per-connection: busy sockets ≈ 2,000 × 0.020 = **40**. With HTTP/2 multiplexing, fewer connections carry more streams—until a loss event stalls the multiplex.

If each debit used a new connection and closed with TIME_WAIT 60 s on the client: 2,000/s × 60 s = **120,000** tuples in TIME_WAIT. Ephemeral ports (often ~28,000 on a default range) exhaust. Errors look like “cannot assign requested address,” not “ledger down.”

NAT idle timeout 30 s with HTTP keepalive 90 s: the NAT drops the mapping; the next byte gets RST. If the ledger already committed, the client sees **UNKNOWN**, not rollback. Same identity on retry. See [tail-latency control](/learn/tail-latency-control) for cancellation that actually stops work.

</Calculation>

Connection **drain** (from the LB lesson) means stop new streams, wait for in-flight, then RST. **Keepalive** is a lie detector with a clock: TCP keepalive, HTTP/2 PING, QUIC max idle. Set them **below** NAT and LB idle so you discover death before a debit.

Kafka produce still rides TCP to brokers. `acks=all` is a **broker** durability contract from [Kafka delivery](/learn/kafka-delivery-and-failure), not HTTP semantics. A TCP RST on the produce socket is UNKNOWN for that record, same as HTTP.

<InteractiveCalculation mode="little-law" title="New connections spend extra hold time in handshake" />

If handshake+TLS adds 40 ms to a 20 ms debit at 2,000 req/s, extra occupancy is 2,000 × 0.040 = **80** connections of handshake work. Pools buy that back. Unbounded pool growth buys TIME_WAIT death.

</UnderTheHood>

<MentalModel title="A reserved lane, not a stamped contract">

A TCP or QUIC connection is a reserved lane on a highway. The lane keeps cars in order. It does not stamp the bank slip. Closing the lane after the clerk stamped the slip does not unstamp it. Opening a second lane with a new slip number is a second payment. 0-RTT is mailing a photocopy of yesterday’s slip before the clerk looks up; someone else can mail it too.

Retain: **order is per connection, reuse is amortization, 0-RTT is replay, RST after commit is UNKNOWN, and QUIC does not replace uniqueness.**

</MentalModel>

**Authoritative:** TokenX ledger plus unique `(tenant, transfer_id)`; Ad Click billed-fact log plus `click_id`. **Derived:** connection pools, congestion windows, LB 5-tuple maps, NAT mappings, QUIC connection IDs. **Consistency boundary:** commit is the ledger or log append, not TCP ACK, not TLS Finished, not HTTP/2 END_STREAM if the client never saw it. Solid edges are acquire, 1-RTT TLS, handler, commit. Dashed edges are forbidden 0-RTT, drain RST, and retry with the same identity. Recovery is drain above p99, keepalive below NAT idle, fail closed if the pool cannot obtain a connection for money, and never mint a new id because the socket died.

<RealExamples title="TokenX no 0-RTT; Ad Click collector reuse">

**TokenX.** Disable early data on the debit hostname. Pool HTTP/2 or HTTP/1.1 with a cap from Little’s Law, not “max 10,000.” On RST or timeout, query or retry the **same** `transfer_id`. Do not hedge POSTs onto two connections with two UUIDs ([tail latency](/learn/tail-latency-control)).

**Ad Click.** High-QPS collectors prefer long-lived TCP or QUIC to the log broker or local disk. Connection reuse amortizes handshake at 80k clicks/s. ACK still waits for durable append. If QUIC 0-RTT replays a packet with the same `click_id`, the log’s unique insert makes it a duplicate, not a second bill—**if** uniqueness is up. If uniqueness is down, do not fail-open an ACK from the socket accept path.

<InterviewTraps title="Connection folklore">

- **“TCP is reliable so the debit happened exactly once.”** Reliable delivery of bytes is not unique business effects.
- **“HTTP/2 killed HOL blocking.”** It killed HTTP/1.1 request HOL. TCP loss still stalls the multiplex.
- **“QUIC is always faster and safer for payments.”** Faster on lossy links maybe; 0-RTT is *less* safe for POST.
- **“Connection reuse means sticky sessions.”** Reuse is a pool. Affinity is a correctness smell for HTTP APIs.
- **“RST means the server rolled back.”** RST after commit is UNKNOWN.
- **“TIME_WAIT is a kernel bug.”** It is a 2MSL guard. Exhaustion is an architecture bug (chatty new connections).

</InterviewTraps>

<Tradeoffs title="Warm sockets versus loss isolation versus replay">

- **Many HTTP/1.1 connections versus few HTTP/2:** isolation versus memory and HOL on loss.
- **QUIC versus TCP+TLS:** better loss recovery and migration; newer middlebox and CPU cost; 0-RTT temptation.
- **Long keepalive versus NAT/LB idle:** discover death early versus extra PING traffic.
- **Large pools versus cap:** handshake avoidance versus holding dead backends and file descriptors.

Spendable writes choose 1-RTT and stable ids over a 40 ms handshake win.

</Tradeoffs>

<InterviewAnswer>

“I budget handshake and slow start separately from service time. Pools amortize TLS 1.3 1-RTT; I disable 0-RTT on TokenX POST /debits because early data is replayable. HTTP/2 multiplexes streams on one TCP congestion context, so a loss stalls siblings—QUIC mostly removes that HOL, not the need for transfer_id. Keepalive has to sit below NAT and balancer idle or the next write RSTs. TIME_WAIT times connections, not money: a new socket per debit will exhaust ephemeral ports. If drain RSTs after commit, the client sees UNKNOWN and retries the same identity. Kafka acks=all is still a broker contract riding TCP, not HTTP exactly-once. Connection reuse is not stickiness and not a ledger.”

</InterviewAnswer>
