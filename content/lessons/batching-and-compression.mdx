<BigPicture title="Amortization buys throughput; it spends latency, CPU, and retry radius">

A batch is a courier van: one fsync, one RPC, one codec frame for *N* records. Compression is packing the van tighter. Neither action creates a write-ahead log, and neither creates **exactly-once** effects. Batching **multiplies** a timeout into *N* retries. Compression **rearranges CPU versus bytes**; it does not fsync.

[Write scaling](/learn/write-scaling) already placed batching next to key ownership and durable ACK. This lesson goes deeper on **linger versus size**, the **first-byte latency tax**, **codec choice**, and the **retry blast radius** when the van crashes. Queueing math for the rest of the path is [Latency, throughput, and queues](/learn/latency-throughput-and-queues). TCP, TLS, and HTTP framing live in [Networking for system design](/learn/networking-for-system-design). Large immutable blobs and multipart retry granularity live in [Object storage and large files](/learn/object-storage-and-large-files). Kafka produce `acks`, ISR, and producer idempotence live in [Kafka delivery and failure](/learn/kafka-delivery-and-failure).

**Authoritative state:** TokenX ledger rows plus unique `(tenant, transfer_id)`; Ad Click **billed-fact log** until retention. **Derived state:** campaign windows, dashboards, HTTP caches, codec output sitting in a memory buffer. **Durability** begins when the named store commits under its ACK policy—not when gzip finishes. **Ordering** is still the partition or row owner, not the batch timer. **Availability** of a linger buffer is not an ACK.

Planning assumptions (illustrative, not a measured cluster): TokenX transfer API **2,000 commits/s**, **800 B** encoded facts, linger **5 ms or 50 records**. Ad Click collector peak **80,000 clicks/s**, **400 B** billed facts, linger **20 ms or 500 records**.

</BigPicture>

<UnderTheHood title="Linger, first byte, retry radius, then codecs">

### Linger versus size: two clocks, one van

A producer (or collector) closes a batch when **either** clock fires:

- **Size / count:** *N* records or *B* uncompressed bytes.
- **Linger:** *T* milliseconds since the first record entered an empty batch.

Fill time at a steady rate is `N / λ`. If fill time is shorter than linger, size wins and the first record waits about `N / λ`, not *T*. If arrivals are sparse, linger wins and the first record pays the full timer.

<Calculation label="Linger versus size, first-byte tax">

TokenX: fill time for a 50-record cap is 50 / 2,000 s⁻¹ = **25 ms**. A **5 ms** linger is shorter, so linger wins. Actual *N* ≈ λT = 2,000 × 0.005 = **10** records, and the first debit waits ≈ **5 ms** of extra hold—the **first-record hold** on the batch path—not 25 ms. Do not amortize *C* against the 50-record cap that never filled.

Ad Click: fill time for a 500-record cap is 500 / 80,000 s⁻¹ = **6.25 ms** at peak. A **20 ms** linger is longer, so at peak the count cap wins and the first click waits ≈ 6.25 ms plus codec and RPC. In a **sparse** window the linger wins: the first click of a quiet campaign waits up to 20 ms in process memory **before** the produce.

Amortization: if a produce + ISR ACK costs **C = 2 ms** of broker work independent of *N*, divide *C* by the *N* that actually ships. TokenX: 2 ms / 10 = **200 µs** per record. Ads at peak: 2 ms / 500 = **4 µs**. You bought that by holding the first record.

</Calculation>

Do not linger TokenX spendable debits for ads-scale *T*. The debit tail SLO is a latency budget; linger is a line item in that budget, same as TLS and lock wait.

### Retry multiplies the batch

One timed-out produce is not one retry. It is **every record in the open batch**. Blast radius = batch cardinality (or uncompressed bytes if you think in network).

<Calculation label="Retry blast radius">

Ad Click: one 500-click batch is 500 × 400 B = **200 KB** uncompressed. A 30 s SDK timeout that retries the whole buffer resends 500 identities. With stable `click_id` on the billed-fact log those are **at-least-once duplicates of identity**. Without ids, a derived 1-minute window can count 500 extra bills.

TokenX: a 50-transfer batch that retries without `(tenant, transfer_id)` uniqueness is 50 possible double-debits. Producer idempotence (broker PID + sequence) can collapse **the same produce batch** inside a producer session; it does **not** collapse two business commands with different transfer ids. See [Kafka delivery and failure](/learn/kafka-delivery-and-failure).

</Calculation>

Batching is not exactly-once. Exactly-once is at best **effect-once inside a named atomic boundary** with a retained identity. Compression does not change that sentence.

### Codecs: CPU versus bytes

Name the required property first: **reduce network and disk bytes** under a **CPU and latency budget**. Codec names second.

Planning ratios on repetitive JSON-like facts (illustrative, not a spec):

| Codec | Typical ratio on 200 KB similar facts | CPU / latency character | Fit |
| --- | --- | --- | --- |
| **lz4** | ~2–2.5× | Lowest CPU, smallest p99 bump | Kafka produce path when brokers or collectors are CPU-bound |
| **zstd** | ~3–4× at modest level | Tunable; often best bytes/CPU | Default for large Kafka batches of similar records |
| **gzip** (deflate) | ~3× | Higher CPU, worse tail | HTTP `Content-Encoding` at a proxy; rarely the Kafka produce codec of choice |

Kafka compresses **the record batch** (the message set), so similar consecutive facts share a dictionary and ratio **improves with batch size**. HTTP gzip usually compresses **one response body**. A 200 B JSON error body plus gzip header and deflate overhead can **grow**. Do not enable gzip on tiny payloads, already-compressed images, or zstd object parts.

<Calculation label="CPU versus network on an Ad Click produce">

Uncompressed peak: 80,000 × 400 B = **32 MB/s** leader payload before protocol headers.

lz4 at 2.2× → ≈ **14.5 MB/s** on the wire, cheap collector CPU.

zstd at 3.5× → ≈ **9.1 MB/s**, more collector cores.

gzip at 3.0× → ≈ **10.7 MB/s**, often the worst p99 of the three on the produce path.

If one collector core compresses at an illustrative **200 MB/s lz4** versus **40 MB/s gzip** input, gzip needs 32 / 40 = **0.8 core** just for codec at peak, while lz4 needs 32 / 200 = **0.16 core**. Replication factor 3 still multiplies **stored** bytes after the codec, not before it, once the broker stores the compressed batch.

</Calculation>

### Kafka batch+compression versus HTTP gzip

**Kafka:** linger + `batch.size` + a codec on the **produce batch**. CPU is paid on the producer (or on the broker if the producer sends uncompressed and the broker re-compresses—usually a mistake you pay twice). Retry is **batch-scoped**. Durability is the log ACK, not the codec.

**HTTP gzip:** typically a reverse-proxy or app `Content-Encoding` on **one response**. It helps large JSON lists and static text. It hurts TokenX 200-byte debit responses: extra CPU, extra first-byte delay, possible size increase. TLS already encrypts; gzip does not replace TLS and does not reduce TLS handshake count—see [Networking for system design](/learn/networking-for-system-design).

**Object storage:** compress **large** immutable exports before or as part of multipart upload when CPU is cheaper than egress and storage. Do not gzip 2 KB metadata objects. Part size still sets retry granularity of the **part**, not of a Kafka batch ([Object storage and large files](/learn/object-storage-and-large-files)).

<InteractiveCalculation mode="event-ingress" title="Peak click bytes before you pick a codec" />

Use the envelope as uncompressed leader ingress. Then apply an **assumed** codec ratio and replication. It is not a broker count and not a durability proof.

</UnderTheHood>

<MentalModel title="Courier van, packing foam, numbered parcels">

Picture a courier van (the batch). **Linger** is “wait for more parcels or leave at T.” The first parcel’s wait is the **first-byte tax**. **Compression** is packing foam: less truck space, more warehouse labor. **Retry** redrives the whole van. If parcels have no tracking numbers, the warehouse books them twice. Foam does not make the vault fireproof: **compression is not durability**. A full van is not a receipt: **batching is not exactly-once**.

TokenX sends small vans so debit tails stay inside the SLO. Ad Click may linger longer and pack more parcels, but the collector still ACKs the SDK **only after** the vault log stamps the batch.

Retain: **size linger against the first record, size N against retry radius, pick a codec from CPU versus bytes, skip tiny and precompressed payloads, ACK only the authoritative log, keep windows derived.**

</MentalModel>

<RealExamples title="TokenX small vans; Ad Click larger linger after log ACK">

**TokenX.** Keep batches small so debit p99 can afford linger, codec, row lock, and commit. Illustrative budget: 5 ms linger, 50 records, lz4 or no compression on 800 B facts that may not share enough dictionary to beat CPU. Uniqueness `(tenant, transfer_id)` stays in the ledger transaction. Do not gzip every 200 B HTTP 200. Do not linger 20 ms because ads do. Write-behind of a debit remains forbidden—the linger buffer is the same class of memory as a write-behind cache until the ledger commits.

**Ad Click Aggregator.** Collectors may linger **20 ms or 500 records**, compress with **zstd or lz4** because consecutive billed facts are similar JSON, then produce. **ACK the SDK after** the billed-fact log accepts the batch ([Kafka delivery and failure](/learn/kafka-delivery-and-failure)). Window sums stay derived. A viral campaign at 80,000 clicks/s fills the count cap in 6.25 ms; the linger timer is for sparse campaigns, not an excuse to ACK early. Object-storage raw-event segments can use a heavier codec because they are large, immutable, and retry by **part**, not by mixing HTTP gzip with Kafka batch settings.

<InterviewTraps title="Batching slogans that fail at IC6">

- **“Larger batches are always faster.”** They raise throughput and the first-byte tax and the retry radius. TokenX debit tails often lose.
- **“gzip everything at the edge.”** Tiny JSON and already-compressed objects can grow or waste CPU. Name a size floor.
- **“zstd is more durable than lz4.”** Codecs do not fsync. Durability is ACK policy and disk/ISR bounds.
- **“Kafka compression is the same as HTTP gzip.”** Batch dictionary versus one HTTP body. Retry scopes differ.
- **“Producer idempotence means exactly-once transfers.”** It deduplicates a produce batch inside a producer session, not two business ids, and not a ledger side effect.
- **“Linger is free because users will not notice 20 ms.”** 20 ms is the entire budget of some debit SLOs once you add lock wait and TLS.
- **“If we compress, we can ACK from memory.”** Compression does not create durability.
- **“Batching gives exactly-once because we flush together.”** One failed ACK retries everyone in the van.

</InterviewTraps>

<Tradeoffs title="What you spend to amortize">

- **Linger versus tail latency:** longer linger fills vans in sparse windows and delays the first record. TokenX spends this reluctantly; ads can spend more **if** ACK still waits for the log.
- **Batch size versus retry blast radius:** large *N* amortizes fsync and helps codec ratio; a timeout resends *N* identities.
- **lz4 versus zstd versus gzip:** CPU and p99 versus bytes on the wire and disk. gzip is often the HTTP tool, not the produce-path tool.
- **Compress versus skip:** large similar batches win; sub-kilobyte and precompressed payloads lose.
- **Kafka batch codec versus HTTP encoding:** one is a produce-path dictionary; the other is a per-response Content-Encoding. Combining them without a size check double-pays CPU.
- **Sync ACK versus collector availability:** holding the SDK until log ACK fails closed; ACKing the linger buffer stays up and hides a loss window.

Correctness of TokenX balances and billed-click identity is not a compression knob. Completeness of a dashboard is.

</Tradeoffs>

<InterviewAnswer>

“I treat batching as amortization, not correctness. Linger and size are two clocks: the first record pays min(T, N/λ), which is a first-byte tax I put inside the SLO. TokenX keeps that tax small—a few milliseconds and tens of records—because debit tail and a 500-wide retry would be a blast radius on money. Ads can linger longer and compress lz4 or zstd because consecutive billed facts share a dictionary, but the collector still ACKs only after the billed-fact log under a named acks policy. Retry resends the whole batch, so every record needs a stable id; producer idempotence only collapses the same produce batch. gzip is an HTTP tool with a size floor—I will not gzip 200-byte debit responses or already-compressed objects. Compression does not fsync. Batching does not create exactly-once. Windows stay derived and rebuild from facts.”

</InterviewAnswer>
