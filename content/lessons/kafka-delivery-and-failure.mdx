<BigPicture title="Delivery semantics belong to a boundary">

Kafka does not magically make a whole business workflow exactly once. It can durably replicate records and coordinate transactional reads and writes inside supported boundaries. Once a consumer calls an external payment API or database, correctness depends on that side effect too.

Design for at-least-once delivery with idempotent effects unless you can name and enforce a narrower transactional boundary.

Durability begins before consumption. With replication factor three, <code>acks=all</code> makes the producer wait for every replica currently in the in-sync replica set—not necessarily every configured replica. <code>min.insync.replicas=2</code> requires at least two in-sync replicas for an acknowledged write; if fewer remain, the broker rejects the write rather than silently weakening the guarantee. That trades write availability for a clearer loss boundary.

Producer idempotence assigns producer IDs and sequence numbers so broker retries do not append the same producer batch twice within the producer session. It does not deduplicate two business commands with different event IDs, and it does not make an external database side effect exactly once.

</BigPicture>

<UnderTheHood title="The offset is part of your correctness protocol">

If a consumer commits its offset before applying a side effect, a crash can lose work: at-most-once behavior. If it applies the side effect first and commits second, a crash can repeat work: at-least-once behavior.

Make repetition safe with a unique event ID. In a relational database, write the business mutation and processed-event marker in one transaction. For outbound events, write an outbox row in that same transaction and publish it asynchronously.

Retries should use capped exponential backoff with jitter. Non-transient failures go to a quarantined dead-letter path carrying original metadata, error class, and replay controls.

Consumer offsets are group progress, not proof that a business effect committed. During a rebalance, ownership can move while a previous consumer still has work in flight. Consumers should stop fetching on revocation, finish or cancel bounded work, commit only completed offsets, and use database constraints or fencing so a stale owner cannot apply an effect twice. Long processing must also respect <code>max.poll.interval.ms</code>, or the group may replace an otherwise healthy consumer.

<MentalModel title="Crash between any two lines">

For every consumer, imagine the process dying before and after each operation: read, compute, write, acknowledge. If either ordering loses or duplicates an unacceptable effect, add idempotency or atomicity.

Think of a coat-check ticket. Kafka's offset says which ticket number the attendant reached; it does not prove the coat reached the correct owner. The sink needs its own claim check—the event ID—and both the claim check and the handoff must be recorded together.

Partitions provide order only within that partition. Consumer groups provide parallel ownership, not global order.

</MentalModel>

Kafka owns replicated log durability and group offsets. The sink database owns the business effect, dedupe marker, and outbox in one local transaction. The boundary between the sink commit and Kafka offset commit is deliberately at-least-once; replay safety closes the gap.

</ArchitectureDiagram>

<RealExamples title="Duplicate orders and analytics replays">

An order-created event may be delivered twice after a rebalance. A uniqueness constraint on <code>event_id</code> makes the second database transaction a no-op. A click counter can instead use windowed state plus offset-aware checkpoints.

TokenX settlement instructions need an idempotency key at the ledger boundary. Email delivery may accept a small duplication risk, but balance mutation cannot.

<InterviewTraps title="Fault-tolerance claims that need correction">

- Saying “exactly once” without defining source, sink, and failure boundary.
- Committing offsets on a timer independent of side effects.
- Retrying a poison record forever and blocking later records in the partition.
- Adding partitions while assuming global ordering remains.
- Ignoring consumer rebalance time and state restoration.

</InterviewTraps>

<Tradeoffs title="Ordering, parallelism, and recovery speed">

More partitions increase parallelism but weaken the practical scope of ordering and raise coordination overhead. Long retention improves replay and debugging but costs storage. A dead-letter topic preserves throughput but creates an operational queue that needs ownership, alerts, and safe replay tooling.

Quarantining a record can violate per-key order because later records may proceed without the missing transition. For state machines, park the entire key, route it to a repair stream, or make later records conditional on a sequence number. A dead-letter topic is inappropriate when skipping one event makes following state uninterpretable.

</Tradeoffs>

<InterviewAnswer>

“I define the guarantee across the source and each side effect. I usually choose at-least-once consumption, then make the database mutation idempotent by storing the event ID in the same transaction. Outbound work uses an outbox. I commit the Kafka offset only after durable success, quarantine permanent failures, and retain enough history for replay. This accepts duplicate delivery while preventing duplicate business effects.”

</InterviewAnswer>
