<BigPicture title="The database is a queue of connections, locks, and pages">

Application CPU is rarely the first database bottleneck. The scarce resources are **connections**, **row locks**, **buffer-pool pages**, and **planner-chosen access paths**. Extra API replicas that share one primary add arrivals to those queues. They do not add cashiers.

Index mechanics, composite keys, and write amplification of extra B-trees are taught in [Indexes and query execution](/learn/indexes-and-query-execution). This lesson stays operational: **pool sizing**, **lock wait versus I/O wait**, **EXPLAIN as a production habit**, **N+1**, **cache-aside versus the primary**, and **read amplification** from secondary indexes and log-structured merge (LSM) trees. Schemas still come from [Data modeling from access patterns](/learn/data-modeling-from-access-patterns). Cache fences live in [Caching patterns and invalidation](/learn/caching-patterns-and-invalidation). Read replicas as a scale-out pattern live in [Scaling read-heavy services](/learn/scaling-read-heavy-services). Hot-row ownership lives in [Write scaling](/learn/write-scaling). Queueing envelopes live in [Latency, throughput, and queues](/learn/latency-throughput-and-queues).

**Authoritative state:** TokenX ledger plus unique `(tenant, transfer_id)`; Ad Click billed-fact log (facts may be queried via a warehouse, but invoices do not come from the ORM cache). **Derived state:** buffer cache, Redis campaign metadata, covering indexes, dashboard joins. **Consistency:** spendable reads use the ledger primary (or a named synchronous standby you are willing to block on). **Durability:** commit of the ledger transaction, not a pool checkout. **Availability:** a full pool that waits forever looks like a hang, not a 503.

Planning assumptions (illustrative): TokenX **2,000** HTTP requests/s, **65%** hit the ledger, mean connection hold **12 ms** on the happy path, p95 hold **40 ms** when a celebrity account is locked. Ad Click aggregator **5,000** window-build requests/s against metadata, plus bursts of **500** click rows per task.

</BigPicture>

<UnderTheHood title="Pools, waits, plans, chatter, amplification">

### Pool size is Little's Law on hold time, not “one per thread”

Define the boundary: **connections busy in this pool**. Arrival rate is requests that **check out** a connection, not total HTTP QPS. Hold time is checkout-to-release, including SQL, client-side mapping, and idle-in-transaction.

`L = λ × W`. Size ≈ `L_p95` plus headroom, capped by `max_connections` on the server **across every app, admin, and migrator**.

<Calculation label="TokenX ledger pool versus whole-request in-flight">

Whole path at 2,000 req/s × 80 ms end-to-end → **160** requests in flight. That is not the pool.

Ledger-using rate λ = 2,000 × 0.65 = **1,300** checkouts/s.

Mean hold 12 ms → L = 1,300 × 0.012 = **15.6** busy connections.

If p95 hold is 40 ms and you provision for that as a sustained mean (conservative), L = 1,300 × 0.040 = **52**. A **70**-connection ledger pool has headroom; a **400**-connection pool matching in-flight HTTP will stampede `max_connections` and still wait on the same row locks.

Celebrity account *A* at an offered 400 transfers/s with **15 ms** exclusive row-lock hold: service rate μ ≈ 1 / 0.015 ≈ **67** commits/s. Offered load is 400 / 67 ≈ **6×** cashier capacity, so utilization is not a stable ρ < 1. Little’s Law does not give a steady queue of `400 × 0.015 = 6` waiters; the lock queue grows until timeouts unless you shed or isolate the key. Throughput of *A* stays ~1/hold-time. Growing the pool from 70 to 200 adds places to wait, not lock throughput. See [Write scaling](/learn/write-scaling).

</Calculation>

**Isolate pools by workload class.** TokenX HTTP must not share the **ledger pool** with analytics `SELECT` that holds a snapshot for 800 ms. Ad Click window builders must not share the **billed-sink pool** with a debug reporter. One saturated class otherwise occupies every connection the debit path needs.

Checkout must have a **timeout**. An unbounded wait converts a lock incident into a thread/async deadlock. On timeout, fail the request; do not start a second checkout for the same debit.

### Lock wait versus I/O wait

**Lock wait:** another transaction owns a row, tuple, or relation lock. CPU may be idle. `wait_event` in PostgreSQL looks like `Lock` / `tuple`. Throughput of that key is about `1 / hold time`.

**I/O wait:** the engine needs pages not in the buffer pool (or a cloud volume is saturated). Same query plan, cold cache, different latency. `wait_event` looks like `DataFileRead`.

They need different fixes. Lock wait: shorten transactions, index the predicate so you lock fewer rows, stop holding checkout while calling HTTP, isolate hot keys. I/O wait: buffer pool sizing, covering indexes, sequential-scan elimination, storage IOPS, vacuum/compaction. Raising `work_mem` does not unstick a row lock. Adding replicas does not unstick a write lock on the primary.

Idle-in-transaction is a hybrid failure: the app checked out a connection, ran `BEGIN`, then waited on Redis or a teammate's debugger. Locks and snapshots stay open. Pool utilization looks “busy” while SQL is not running.

### EXPLAIN: sequential scan versus index, estimated versus actual

Treat `EXPLAIN` (and `EXPLAIN ANALYZE` in a safe environment) as an operational check, not a textbook exercise. Look at:

- **Node type:** sequential scan on a 50 M-row `ledger_entries` for one `wallet_id` is a missing or unused access path.
- **Estimated versus actual rows:** stale statistics send the planner into a nested loop that explodes.
- **Heap fetches** after an index scan: not covering; each row may become another page read (**read amplification**).
- **Sort / HashAggregate** spilling to disk: `work_mem` and batch shape, not “the index is broken.”

Details of B-tree height and `INCLUDE` columns stay in the [indexes lesson](/learn/indexes-and-query-execution). Here the production move is: **the p99 query is the plan you have, not the index you intended.**

### N+1: chatty ORM, not a slow disk

N+1 is one query for a parent list plus one query **per child**. The planner of each child query can be perfect. The round trips still dominate.

Ad Click: load 500 billed clicks, then `GET /campaigns/{id}` or `SELECT * FROM campaigns WHERE id = ?` inside a loop. At 2 ms each, that is **1 s** of serial chatter before the window function runs. The fix is a bounded `WHERE campaign_id IN (...)` (chunked), a join, or a **cache-aside** of immutable campaign metadata with a version key—not 500 nested lazy loads.

TokenX: listing 50 ledger lines then querying `users` per `actor_id` is the same bug. It is not “Postgres is slow.”

### Covering indexes versus write amplification, cache-aside versus DB

A **covering** index (or `INCLUDE`) removes heap fetches: **read amplification down**, **write amplification up** because every debit now maintains more bytes. That trade is worth it for wallet-history p99; it is not worth a low-selectivity boolean on every row. Do not re-teach index design here—measure whether the operational p99 is heap fetch or lock wait.

**Cache-aside** belongs on **derived** reads: campaign name, creative URL, TokenX **token metadata**. Miss path is the database; stampede protection is singleflight, not a bigger pool ([Caching patterns and invalidation](/learn/caching-patterns-and-invalidation)). Spendable balances stay on the ledger checkout. A 99% hit rate that is wrong is still wrong, and a flush turns the pool into the origin.

<Calculation label="Ad Click N+1 versus one indexed IN-list">

500 clicks × 1 campaign lookup × 2 ms RTT = **1,000 ms** serial.

One `SELECT ... WHERE id IN (…)` of 80 distinct campaign ids via primary key: a few milliseconds plus **80** buffer hits if hot.

Cache-aside at 95% hit: origin rate = 5,000 window tasks/s × 0.05 = **250** metadata reads/s, not 5,000 × 80.

If each miss does a nested-loop join that reads 12 LSM SSTables (illustrative read amp 12×), those 250 reads become **3,000** file touches/s. The cache did not make the LSM authoritative; it hid amplification until the flush.

</Calculation>

### Read amplification: secondary indexes and LSM

**Secondary index in a heap table:** index leaf → heap tuple. One logical point read can be **two+ page reads**, more with MVCC visibility and wide rows.

**LSM / clustered secondary:** a secondary key lookup may return a primary key, then a second search into the base SSTables. Compaction reduces future amp and costs write I/O now. Bloom filters bound negative lookups; they do not bound a hot campaign whose keys sit in many levels.

Count amplification in **page reads or SSTable touches per user query**, not in “we have an index so it is O(1).”

</UnderTheHood>

<MentalModel title="A limited number of phone lines into a bank vault">

The database is a vault with **few phone lines** (the pool). Callers who stay on the line while they chat with someone else (idle-in-transaction, N+1, HTTP inside a transaction) occupy a line. A second queue inside the vault is the **single cashier for account A** (row lock). A third delay is the clerk **walking to the archive room** (I/O wait / sequential scan / LSM levels). Photocopies of campaign posters (cache-aside) save trips for derived data; they are not the vault ledger.

Retain: **size pools with λ × hold time, isolate money from reports, name lock wait versus I/O wait, fix N+1 before buying hardware, treat covering indexes and LSM levels as amplification, cache only derived reads.**

</MentalModel>

<RealExamples title="TokenX isolates the ledger pool; Ad Click kills campaign N+1">

**TokenX.** Two pools: **ledger** (small, low timeout, no sequential scans allowed) and **replica-analytics** (larger hold time, admission-controlled). Debit: checkout ledger, insert `(tenant, transfer_id)`, update balance, commit, release—**then** produce outbox. History pagination uses the covering access path from the indexes lesson; if EXPLAIN shows a sequential scan, that is an incident, not a cache miss. Celebrity account lock wait is visible as `Lock` wait_event while CPU is idle; operators must not scale the API HPA on CPU. Cache token **metadata** only.

**Ad Click Aggregator.** Window builders must not N+1 campaign rows for each click. Distinct `campaign_id` set → one indexed read or a cache-aside with TTL jitter. Billed facts remain the log; the aggregator database is a **sink** with its own pool, isolated from debug queries. A viral campaign that turns a nested-loop join into a sequential scan on facts is a plan problem plus skew, not a reason to cache invoice totals as authority. If the sink is LSM-backed, budget read amplification on the campaign-secondary index after compaction falls behind.

<InterviewTraps title="Database-performance slogans that fail at IC6">

- **“Set pool size to number of API threads.”** Size λ × hold time, then cap by server `max_connections`.
- **“p99 is I/O, buy a bigger disk.”** Check `wait_event`. Lock wait and N+1 fake a storage story.
- **“We have an index, so EXPLAIN is optional.”** The planner may still sequential-scan with stale stats or a non-leftmost predicate.
- **“N+1 is fine in a VPC.”** 500 × 2 ms is still a second. Latency is not a bandwidth coupon.
- **“Covering indexes are free reads.”** They tax every write. Count write amplification.
- **“Cache the ledger; the pool is the problem.”** The pool is scarce because the working set and locks are. Spendable state stays authoritative.
- **“LSM is O(1) point lookup.”** Amplification is SSTables and levels, especially on secondary keys.
- **“Raise max_connections to 5,000.”** Each session has memory. You moved the queue into the engine.
- **“Read replicas fix lock wait on UPDATE.”** Replicas do not take the primary's write lock.

</InterviewTraps>

<Tradeoffs title="What you spend to make the primary fast">

- **Small isolated ledger pool versus convenience:** isolation protects debit checkout and forces analytics onto replicas or batch windows. Two pools are operational complexity.
- **Checkout timeout versus patience:** timeouts shed work and surface incidents; too-tight timeouts retry-storm the lock they already lost.
- **Covering index versus write amplification:** wallet-history p99 versus extra bytes on every debit.
- **Cache-aside versus always hitting the DB:** origin offload for derived metadata versus stampede, skew, and forbidden balance caching.
- **Batch IN-list / join versus ORM convenience:** fewer round trips versus loading graphs the product does not need.
- **Buffer-pool / compaction spend versus replica-read offload:** I/O wait and LSM amp are storage-engine knobs; they do not replace access-path design.

Correctness of TokenX balances is not a pool-size knob. Dashboard freshness is.

</Tradeoffs>

<InterviewAnswer>

“I size database pools with Little's Law on the checkout boundary: arrival rate of queries that actually hold a connection times hold time, plus headroom, capped by the server’s max_connections. TokenX keeps a small ledger pool isolated from analytics so a sequential scan cannot occupy debit slots, and checkout has a timeout. I split lock wait from I/O wait: a celebrity account is one cashier, so extra connections and extra API replicas only lengthen the lock queue; I/O wait wants plans, covering indexes, and buffer hits. I read EXPLAIN for the p99 query—estimated versus actual rows, seq scan versus index, heap fetches as read amplification. N+1 is a round-trip bug even when each child index looks perfect; Ad Click campaign metadata gets one IN-list or a derived cache-aside, never a loop. LSM and secondary indexes multiply page touches; I count them. I never cache spendable balances. Durability is the ledger commit with (tenant, transfer_id), not a pool checkout or a Redis TTL.”

</InterviewAnswer>
