<BigPicture title="Bytes in the warehouse; the ledger is the paper">

Prompt: **Design a file storage service** (Dropbox/Drive-class): upload, download, list, share, sync, recover.

**Authoritative control plane:** metadata DB — owner, ACL, current version pointer, size, checksum, scan status, `UPLOADING | AVAILABLE | TOMBSTONED`.

**Authoritative data plane:** object store — immutable keys such as `tenant/object_id/version`. Replacing content writes a **new** version; one metadata transaction swings the pointer.

Clients upload through short-lived signed URLs. The API never proxies terabytes. TokenX statements and Ad Click creatives may live here; spendable balances and billed click uniqueness do **not**. See [object storage](/learn/object-storage-and-large-files) and [CDNs](/learn/cdns-and-edge-architecture).

</BigPicture>

<UnderTheHood title="Multipart, finalize, then the races">

### Capacity (illustrative)

50 million users, 1 billion objects, mean object 2 MB, 5% daily read, 0.5% daily write, 16 MB multipart parts, 10 Gbps NIC for a cache miss path (planning, not a promise).

<Calculation label="Storage and part counts">
Logical bytes = 1e9 × 2 MB = 2 PB

With 3-way erasure or RF-equivalent storage ≈ 2–3× depending on class — name the class, do not invent 3× without a code

A 2 GB video at 16 MB parts = 128 parts; incomplete uploads need a lifecycle abort

Daily write bytes = 0.5% × 2 PB = 10 TB/day ingest before replication
</Calculation>

The event-ingress widget is calibrated for log records in the 100–5,000 B range, not 2 MB objects. Keep object-byte math in the static calculation above; do not pretend a Kafka-style envelope is a multipart part.

### Upload protocol

1. Authenticate; create metadata row `UPLOADING` with unguessable key, max bytes, content policy, expiry.
2. Return signed part URLs constrained to that key and part range.
3. Client PUTs parts; each part has a checksum.
4. `CompleteMultipart` verifies parts, size, checksum; malware scan may be async with `SCANNING`.
5. One metadata transaction: `UPLOADING → AVAILABLE` (or `REJECTED`). Readers never follow a pointer to a partial object.

Download: authz in metadata, then signed GET or CDN with a cache key that includes version. Purge on new version. Private TokenX documents: `private, no-store` at the edge.

Sync: device checkpoints a **cursor per folder**, not “download everything.” Conflicts: last-writer-wins on office docs is a product choice you must name; it is illegal for TokenX ledger files.

Sharing: ACL rows in metadata, not in the object header. Revoke is a metadata write plus short-lived URL expiry; CDN may serve until TTL unless you purge.

DR: object versioning + metadata PITR. Restore testing required ([backup](/learn/backup-restore-and-disaster-recovery)). Orphan bytes without metadata are garbage, not user files.

<RealExamples title="Resume, share revoke, ransomware">

**Resume:** client retries remaining parts; finalize is idempotent on the version id.

**Revoke a shared link:** metadata deletes the token; signed URLs expire in minutes; CDN may still hit until TTL.

**Ransomware on a client:** object versioning plus time-hold; restore is metadata pointer rollback plus byte versions, not “undelete Kafka.”

<Tradeoffs title="Convenience versus isolation">

**Immutable versions + pointer:** cheap rollback; storage growth.

**In-place overwrite:** smaller bill; no restore granularity.

**CDN:** redirect p99; revoke delay.

**Client-side encryption:** privacy; loss of server-side search and scan.

</Tradeoffs>

<InterviewAnswer>

“I split a file product into a transactional metadata database and an immutable object store. Upload creates an UPLOADING row and signed multipart URLs. Finalize verifies checksums and swings a version pointer in one metadata transaction so readers never see partial bytes. CDN and search indexes are derived from that pointer.

I size storage from object count times mean size, I abort incomplete multipart, and I expire signed URLs so revoke is metadata plus TTL. TokenX may store statements here; it does not store balances here.”

</InterviewAnswer>
