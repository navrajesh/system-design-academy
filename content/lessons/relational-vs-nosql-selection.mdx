<BigPicture title="Pick the guarantee before the product name">

“SQL or NoSQL?” is usually the wrong first question. Start with the operations that must be correct, the queries that must be fast, the expected scale, and what the system may do during failure. A relational database is often the simplest home for multi-row invariants and evolving queries. A key-value, document, or wide-column store can be excellent when access paths are known and independent partitions dominate.

The categories overlap. Relational systems can store JSON and distribute data; NoSQL systems may offer transactions and secondary indexes. Compare the exact database and configuration, not a slogan.

For TokenX, the authoritative balance and ledger need atomic constraints and a clear serial order. For the Ad Click Aggregator, immutable events and campaign-window counters favor append-oriented and partitioned stores. One architecture can use both, provided only one store owns each fact.

See [Partitioning vs Sharding vs Aggregation](/learn/partitioning-vs-sharding-vs-aggregation) for placement mechanics and [Data Modeling from Access Patterns](/learn/data-modeling-from-access-patterns) for schema design.

</BigPicture>

<UnderTheHood title="Turn requirements into a storage decision">

### 1. Classify invariants

TokenX must prevent negative spendable balances, conserve token supply, and return the same result for one idempotency key. A database transaction can lock or validate both wallet rows, append balanced ledger entries, and store the idempotency result atomically.

An ad click is different. The raw event is immutable and duplicates can be detected by event ID. Campaign counters are derived and can be rebuilt. This supports an append log plus a partitioned aggregate store.

### 2. Enumerate access patterns

- Point lookup: balance by <code>(wallet_id, asset)</code>
- Multi-row mutation: debit one wallet and credit another
- Range scan: wallet transfers ordered by time
- High-volume append: click events by campaign and event time
- Aggregate read: clicks by campaign and minute
- Ad hoc analysis: cross-campaign reporting over historical events

A key-value store makes point lookup cheap but does not create an efficient range or join automatically. A document store keeps an aggregate together, but unbounded embedded arrays turn one document into a contention and size hotspot. A wide-column store handles partition-local ordered rows well, but partition-key mistakes require application-level scatter.

### 3. Evaluate the physical write path

Many relational engines use a write-ahead log (WAL), buffer cache, and B-tree indexes. A commit becomes durable when the log reaches the required durability boundary; indexes add random page work and write amplification.

Many high-write NoSQL engines use a log-structured merge tree (LSM): append to a WAL, update an in-memory table, flush sorted files, then compact. This favors sustained writes but moves cost into compaction and can amplify reads across files until indexes or Bloom filters eliminate misses.

<Calculation label="Why access shape matters">
TokenX peak transfers = 4,630/s

Each transfer writes 1 transfer row + 2 balance rows + 2 ledger entries + 1 outbox row

Logical row mutations ≈ 4,630 × 6 = 27,780 mutations/s before indexes and replication

Ad clicks at 100M/day and 10× peak ≈ 11,600 events/s, mostly independent appends
</Calculation>

The similar order of magnitude hides different correctness needs. TokenX benefits from a transactionally rich authority. Click ingestion benefits from append throughput and partition-local work.

<MentalModel title="Choose a workshop, not a label">

A relational database is a workshop with shared jigs and inspectors: coordinated work is easy, but every shared constraint can become contention. A partitioned key-value store is a row of independent workbenches: parallel work flies when each job stays at one bench, but cross-bench coordination is your problem.

Retain three questions: **What fact is authoritative? Which operations must be atomic? Which access paths dominate?** Pick the smallest operational model that answers all three.

</MentalModel>

<RealExamples title="TokenX authority and Ad Click scale">

### TokenX: relational first

At roughly 4,630 peak transfers per second, a well-designed transactional database may have substantial headroom. Use constraints, deterministic row-lock ordering, balanced ledger entries, and an outbox. Do not split balances across independent stores because one offers faster reads.

If one ledger later reaches measured limits, preserve the same invariant with distributed SQL, account ownership, escrow, or reservations. “Move to NoSQL” is not a protocol.

### Ad Click Aggregator: append and derive

Raw clicks belong in a durable append log or object-backed event archive. Counters keyed by campaign and minute can live in a wide-column or key-value store whose partition key matches reads. Cross-campaign BI queries belong in a columnar analytical store, not the low-latency counter database.

<InterviewTraps title="Questions behind SQL versus NoSQL">

- **“NoSQL scales horizontally.”** Ask which partition key, consistency level, secondary-index path, and resharding protocol make that true for this workload.
- **“SQL cannot scale.”** Ask for the measured limit. Read replicas, partitioning, distributed SQL, and workload isolation cover many systems before application-managed transactions are justified.
- **“We need schema flexibility.”** Flexible writes move compatibility checks to readers. Explain validation, versioning, backfill, and mixed-version behavior.
- **“Use one database for simplicity.”** One operational product can still contain multiple workload classes. Keep one authority per fact and add derived stores only when the benefit exceeds synchronization cost.
- **Follow-up: what happens during failover?** State whether writes stop, whether stale reads continue, how leaders are fenced, and which committed point clients may observe.

A defensible answer names a concrete property—serializable transactions, partition-local range scans, sustained append throughput—not a category preference.

</InterviewTraps>

<Tradeoffs title="Flexibility, coordination, and operational cost">

Relational modeling gives constraints, joins, and query flexibility, but secondary indexes and cross-partition transactions increase write and coordination cost. Key-value and wide-column models make chosen paths predictable, but new queries often require new tables or pipelines. Document models align with bounded aggregates, but denormalization creates update fan-out and conflict rules.

Polyglot persistence is inappropriate when the team cannot operate several recovery procedures or when duplicated data has no explicit owner and rebuild path. A single proven database with deliberate indexes is often the highest-scale design the organization can safely run.

</Tradeoffs>

<InterviewAnswer>

“I choose storage from invariants and access patterns, not SQL versus NoSQL branding. TokenX needs an atomic, auditable balance mutation, so I start with a serializable relational ledger containing balances, double-entry rows, idempotency, and an outbox. Kafka then feeds replayable history and analytics stores, which never authorize spending.

For ad clicks, raw events are immutable appends and counters are partition-local derived state, so a log plus wide-column or key-value aggregates fits better. I quantify peak writes, bytes, retention, skew, index amplification, and recovery objectives, then test the actual database configuration. Polyglot storage is justified only when every copy has one named authority, staleness contract, and rebuild path.”

</InterviewAnswer>
