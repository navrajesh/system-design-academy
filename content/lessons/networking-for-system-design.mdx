<BigPicture title="The network is part of the distributed system">

Remote calls can be slow, duplicated, or fail with an ambiguous outcome. TCP preserves byte order **within one connection**, but independent connections and concurrent application requests can complete in a different order from submission. A timeout means the caller stopped waiting; it does not prove the server did no work.

Treat every hop as a budgeted, observable failure boundary.

</BigPicture>

<UnderTheHood title="Trace the request">

DNS resolves a name, often through multiple caches. The client opens or reuses a TCP connection, negotiates TLS, and sends HTTP. A load balancer selects a healthy backend, which may make further pooled calls.

L4 load balancers route connections using transport metadata. L7 proxies understand HTTP, enabling path routing, header policies, retries, and richer telemetry at additional processing cost.

Set a decreasing deadline budget down the call chain. Retry only transient failures, only when the operation is idempotent or carries an idempotency key, and with jitter.

<MentalModel title="A timeout creates uncertainty">

After a timed-out transfer request, the safe question is not “should I retry?” It is “can I retry this operation without applying it twice?” Carry a stable operation ID so the receiver can return the first result.

Think of sending a signed form by courier. Losing the delivery receipt does not mean the office never stamped the form. Resending is safe only when the office recognizes the same form number and returns the original result.

</MentalModel>

<ArchitectureDiagram title="A request, its deadlines, and failure boundaries" chart={"flowchart LR\n  U[Client + idempotency key] -->|DNS TTL| DNS[Recursive resolver]\n  DNS -->|address set| E[Edge / CDN]\n  E -->|TLS + remaining deadline| L7[L7 load balancer]\n  L7 -->|health-aware route| S[Stateless service]\n  S -->|bounded acquire| P[Connection pool]\n  P -->|transaction| D[(Authoritative DB)]\n  S -. trace context .-> T[Telemetry]\n  D -. ambiguous commit after timeout .-> S\n  U -. capped retry + jitter .-> E"}>

DNS owns cached routing hints, not health truth. The load balancer owns backend selection, the service owns deadline propagation, and the database owns committed state. A deadline crosses every hop; a timeout response crosses none of the commit boundary automatically.

</ArchitectureDiagram>

<RealExamples title="Static assets and TokenX transfers">

A CDN can terminate TLS near users and serve immutable assets without reaching origin. API responses need cache keys that include relevant authorization and variation headers.

A TokenX transfer timed out after submission may already be committed. Retrying with the same idempotency key is safe; generating a new key risks a second transfer.

<InterviewTraps title="Networking assumptions that break">

- Treating DNS changes as instantaneous despite caches and TTLs.
- Retrying non-idempotent requests at several layers.
- Giving every downstream the full user-facing timeout.
- Health-checking a process without checking whether it can serve dependencies.
- Ignoring connection pool exhaustion and TLS handshake cost.

</InterviewTraps>

<Tradeoffs title="Smarter proxies versus simpler paths">

L7 policy is expressive but adds a hop and operational surface. Long-lived connections amortize handshakes but complicate load distribution during scale-out. Aggressive health checks detect failure quickly but can create false positives during transient load.

Automatic retries become inappropriate when several layers retry independently, when remaining deadline is insufficient, or when the operation lacks a stable idempotency identity. L7 proxying is unnecessary for opaque high-throughput transport that only needs connection routing and would pay for unused HTTP policy.

</Tradeoffs>

<InterviewAnswer>

“I trace DNS, connection establishment, TLS, edge, load balancer, service, and downstream pools. Every call gets a deadline shorter than its caller's remaining budget. Retries are capped, jittered, and restricted to transient failures plus idempotent operations. I monitor connection saturation, handshake rate, status codes, and per-hop latency, because a remote call is never just a function call.”

</InterviewAnswer>
