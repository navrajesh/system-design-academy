<BigPicture title="Consistency is an observable contract">

A consistency model constrains which results concurrent clients may observe. It is not the same as durability, availability, or “the data looks right eventually.” The right model is operation-specific: TokenX balance authorization needs a current ordered decision, while an Ad Click dashboard can show a labeled, bounded-old aggregate.

**Linearizability** makes each single-object operation appear to take effect once between invocation and response, respecting real-time order. **Serializability** makes committed transactions equivalent to some serial order, but that order need not respect wall-clock completion. **Strict serializability** provides both transactional serializability and real-time order. Naming these separately prevents a common interview error.

</BigPicture>

<UnderTheHood title="From histories to guarantees">

Suppose write `W1` completes before read `R1` begins. A linearizable register requires `R1` to see `W1` or a later write. A serializable database could legally serialize a later transaction before an earlier completed one unless it also promises strict serializability. Snapshot isolation provides a consistent snapshot but may permit write skew across independently written rows.

Other useful contracts are weaker but intentional:

- **Causal consistency:** if B was created after observing A, anyone who sees B must also see A. Concurrent unrelated writes may appear in different orders.
- **Read-your-writes:** a session sees its prior writes, often by carrying a minimum log position.
- **Monotonic reads:** a session never goes backward to an older version.
- **Monotonic writes:** one client's writes apply in issue order.
- **Bounded staleness:** a read is at most a stated time or version distance behind.
- **Eventual consistency:** absent new writes and failures, replicas converge; it says nothing about the interim order or duration unless bounded separately.

Clock age alone is an unsafe freshness proof when clocks can skew or replication is stalled. Version distance is stronger when a common ordered log exists. A 5-second bounded-staleness SLO also needs overload behavior: reject, fall back to the leader, or explicitly return older data with its age.

Quorum arithmetic does not name the model by itself. `R + W > N` gives overlap only under stable membership and the intended replica set. A read still needs version comparison, conflict handling, and protection from a deposed writer. Sloppy quorums and last-write-wins timestamps can violate linearizability despite numerical overlap.

</UnderTheHood>

<MentalModel title="Consistency is the editing policy for a shared document">

Linearizability is one live document where completed edits are immediately authoritative. Serializability is a stack of multi-page edits that can be arranged into a valid order. Causal consistency preserves replies after the messages they answer. Eventual consistency promises all copies will converge after editing stops, without promising what readers see meanwhile.

Retain three questions: which operations must agree, which order must be preserved, and what may a client observe during lag or partition?

</MentalModel>

<RealExamples title="Different operations, different contracts">

**TokenX.** Transfer creation and available-balance authorization require one current order; use strict serializability or an equivalent sequenced invariant. Wallet history can lag if the UI carries the transfer receipt and an as-of position. A stale history view must never authorize another debit.

**Ad Click Aggregator.** Live dashboards can be bounded-stale and corrected after late events. Invoice close requires a stable input version and deterministic replay, not merely “eventual.” Causal consistency is useful when a campaign edit must be visible before metrics labeled with the new campaign version.

<InterviewTraps title="Consistency language that sounds stronger than it is">

1. **“Serializable means real-time.”** It constrains transaction equivalence; strict serializability additionally respects real-time order.
2. **“Eventual consistency means a few seconds.”** Eventual has no time bound. State a bounded-staleness SLO and failure behavior if time matters.
3. **“A leader makes reads linearizable.”** A stale or deposed leader can serve old data unless the read proves current authority or uses a quorum/read-index protocol.
4. **“Read-your-writes is global consistency.”** It is a session guarantee and says little about what other clients observe.
5. **“Timestamps establish order.”** Wall clocks skew and can move; use logical or hybrid mechanisms with explicit uncertainty assumptions.
6. **“One model for the service.”** Classify commands, authorization reads, derived feeds, analytics, and offline exports separately.

</InterviewTraps>

<Tradeoffs title="Stronger observation versus coordination cost">

- Linearizable operations simplify current-state reasoning but require coordination and may reject or wait during partitions.
- Causal consistency preserves meaningful dependencies with more availability, but dependency metadata and session routing add complexity.
- Bounded staleness gives a product-visible limit, but the system must shed, wait, or fall back when no replica meets it.
- Eventual views scale and survive disconnection, but are inappropriate for uniqueness, spend authorization, or irreversible decisions without another authority.
- Strict serializability is powerful for multi-row invariants; hot contention can make reservations, partitioned ownership, or redesigned invariants necessary.

</Tradeoffs>

<InterviewAnswer>

“I define consistency per operation. Linearizability is a real-time guarantee for individual operations; serializability is a valid transaction order, and strict serializability provides both. TokenX transfer authorization needs a current, strictly ordered invariant, while history can be an eventual projection if it exposes an as-of position and never authorizes spending.

For sessions I carry the commit position and route only to a replica that has applied it, otherwise I wait within deadline or use the leader. Causal and bounded-stale models are useful when their weaker observations are acceptable. I do not infer linearizability from quorum arithmetic alone. See [replication and failover](/learn/replication-and-failover), [transactions across boundaries](/learn/transactions-across-boundaries), and [CAP and practical consistency](/learn/cap-and-consistency-models).”

</InterviewAnswer>
