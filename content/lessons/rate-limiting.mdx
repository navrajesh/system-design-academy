<BigPicture title="A turnstile, not a unique stamp">

[Backpressure and overload](/learn/backpressure-and-overload) already treated rate limits as **admission**, not uniqueness. [Graceful degradation](/learn/graceful-degradation) decided **what you stop first**. This lesson is the **mechanism**: token bucket, leaky bucket, fixed window, sliding window / sliding log, local versus Redis versus eventual counters, and key choice.

Module 7 **Design a Rate Limiter** is a later mock interview. Here you learn the algorithms and failure modes so that mock is not a vocabulary quiz.

A 100 req/s cap does **not** make TokenX transfers unique. It does not make Ad Click `click_id` unique. If the limiter store is down, you must say whether you **fail closed** (refuse work you promised to cap) or **fail open** with a local degraded cap (keep billed ingest).

</BigPicture>

<UnderTheHood title="Buckets, windows, keys, then the store is down">

### Algorithms

- **Token bucket:** tokens refill at rate *r*, bucket holds burst *b*. A request costs 1 (or N) tokens. Allows bursts of *b*, then steady *r*. Good default for APIs.
- **Leaky bucket:** queue leaks at *r*. Burst is queue depth. Shapes traffic smoother; adds latency (a queue) instead of instant 429.
- **Fixed window:** count in wall-clock 1 s bins. Cheap. Burst of 2× at the window edge (last ms of T plus first ms of T+1).
- **Sliding window / sliding log:** approximate or exact counts over the last T seconds. Fairer; more memory (log of timestamps) or more Redis ops.

<Calculation label="Tenant cap and a Redis race (illustrative)">

TokenX tenant cap **100 req/s**, burst **20**, window 1 s. Token bucket: refill 100 tokens/s, capacity 120 if you fold burst into the bucket, or capacity 20 plus rate 100—**say the parameters**. At 2,000 global req/s and 50 tenants, mean 40 rps/tenant; a celebrity tenant at 400 rps is 429 after burst.

Redis `INCR` + `EXPIRE` without a transaction: a crash after INCR before PTTL can leak a key that never expires (**permanent 0 rps** if you treat existence as a lock) or, with GET+SET, lose counts. Use atomic `INCR` with `EXPIRE NX` on first increment, or a Lua script. Clock skew on sliding windows across replicas: a 200 ms skew on a 1 s window is a **20%** fairness error. Label it.

Hot key: one campaign_id at 50k rps into one Redis shard. The limiter becomes the bottleneck. Shard by key; do not make the limiter a global lock for all ads.

</Calculation>

### Where it runs

Edge / mesh / app / gateway can all 429. Pick **one** user-visible limiter for a class, or you stack 429s without a coherent Retry-After. Local in-process limits survive Redis loss but do not coordinate across replicas: *N* replicas × 100 rps = **100N** rps. Central Redis coordinates and adds a failure mode.

**Limiter store down:**

- **TokenX abuse/fraud cap you advertised:** **fail closed**. Unlimited spendable POSTs during a Redis outage is a product incident. 503 with Retry-After is honest.
- **Ad Click public ingest:** often **fail-open** to a **local** degraded cap (e.g. 10% of normal, or a static per-pod cap) so a Redis outage does not drop the billed path. Uniqueness stays at the log. Dashboards may miss sampled debug.

This is the same fail-closed money / fail-open ingest split as degradation, applied to the turnstile.

If you queue instead of 429, occupancy is the leaky-bucket depth. That is extra latency, not extra uniqueness.

<MentalModel title="A nightclub turnstile">

The bucket is a turnstile that lets 100 people per second and 20 in a rush. Redis is the shared clicker. If the clicker breaks, a bank (TokenX) closes the door; a stadium (ads ingest) uses a local usher with a lower number. The turnstile never stamps tickets—that is uniqueness at the vault.

Retain: **rate is admission, keys define fairness, the store’s outage needs a named fail mode, and 429 is not a commit.**

</MentalModel>

<RealExamples title="TokenX tenant fail-closed; ads local fail-open">

**TokenX.** 100 rps/tenant, burst 20, key `tenant_id`. Fraud team requires the cap even during Redis loss → fail closed. Transfers that got through still need `transfer_id`. Rate limit does not replace [idempotency](/learn/idempotency-and-deduplication).

**Ad Click.** Per-campaign 10k rps plus a global bot IP list. Redis outage: each collector enforces 2k rps local. Some campaigns exceed the global cap until Redis returns—**named**. Billed `click_id` still unique. Debug produce is sampled first ([graceful degradation](/learn/graceful-degradation)).

<InterviewTraps title="Limiter folklore">

- **“Rate limiting gives exactly-once.”** It gives 429s.
- **“Redis INCR is a ledger.”** It is a counter with a TTL.
- **“Fail-open is always more available.”** For TokenX fraud caps it is more stealable.
- **“One global key is simplest.”** It is a hot shard and a fairness disaster.
- **“Fixed windows are equivalent to token buckets.”** Edge burst of ~2× disagrees.
- **“This lesson is the Module 7 rate limiter design.”** That mock still needs distributed config, multi-DC, and interview narrative.

</InterviewTraps>

<Tradeoffs title="Coordination, burst, and who suffers the 429">

- **Local versus Redis versus gossip:** correctness of the cap versus availability of the path versus approximate fairness.
- **Burst versus smooth leak:** UX for mobile retries versus queueing delay.
- **IP versus tenant versus campaign:** NAT and bots versus hot keys.
- **Fail closed versus local degraded:** fraud versus ingest availability.

</Tradeoffs>

<InterviewAnswer>

“I use a token bucket as the default: rate r, burst b, key on tenant or campaign—not a shared NAT IP unless I am fighting bots. Fixed windows hide a 2× edge burst; sliding windows cost more storage and care about clock skew. Redis INCR must be atomic with expiry; the counter is derived admission, not a ledger. If Redis dies, TokenX fail-closes spendable APIs because we advertised a fraud cap; Ad Click collectors fail-open onto a local degraded cap so ingest survives, with click_id uniqueness still on the log. 429 is not uniqueness, not Kafka acks, and not exactly-once. I do not stack edge, mesh, and app limiters with three different windows without naming one user-visible policy.”

</InterviewAnswer>
