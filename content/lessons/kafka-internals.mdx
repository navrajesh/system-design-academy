<BigPicture title="A partition is an ordered log, not a magic bus">

Kafka stores each partition as an append-only, offset-addressed log. Producers append; followers copy; consumers read a prefix that the cluster is willing to treat as stable enough to expose. That prefix is not “everything the leader has ever seen,” and the disk files are not immortal.

The properties to name first: **one ordered log per partition**, **one leader replica that accepts writes**, **followers that pull to catch up**, **one cluster metadata authority** that assigns leadership and records membership, and **finite retention**. Kafka Raft (KRaft) versus ZooKeeper is an implementation of that metadata authority, not a different storage model.

This lesson stays on the broker’s log, replica, and metadata machinery. Acknowledgement policy, `min.insync.replicas`, unclean leader election, and producer idempotence are the durability envelope taught in [Kafka delivery semantics and failure](/learn/kafka-delivery-and-failure). Internals explain *what those knobs sit on*: segments, indexes, log-end offset, high-watermark, in-sync replicas, and page-cache behavior.

TokenX should key ledger-ish streams by wallet or account so one account’s transfers share append order. The Ad Click Aggregator should key ingest by campaign or collector and expect skew: a viral campaign is a hot partition, not a balanced average.

</BigPicture>

<UnderTheHood title="Segments, replicas, watermark, controller, retention">

### The partition is a chain of segments

A partition log is a sequence of **segments**. One **active segment** receives new appends. When it hits a configured size or roll interval—**planning default: 1 GiB** per segment, not a protocol law—the broker seals it. Sealed segments are **immutable** byte files. They are still the authoritative record bytes until retention or compaction deletes them.

Each segment typically has:

- the **log file** (authoritative record batches and offsets)
- an **offset index** mapping a sparse set of offsets to byte positions
- a **time index** mapping timestamps to offsets

Indexes are **derived**. After an unclean process crash, recovery may truncate a torn last batch, then **rebuild indexes from the log**. If the log file and the index disagree, trust the log and reconstruct the index—not the other way around.

### Leader, followers, log-end offset, high-watermark, ISR

Each partition has **one leader**. Producers append to it. Followers are not independent writers; they **fetch** the leader’s log and append locally.

- **Log-end offset (LEO)** is how far a replica has locally written (the next offset it would assign).
- **High-watermark (HW)** is how far **every replica currently in the in-sync replica set (ISR)** has that log. Kafka treats HW as **exclusive**: consumers may fetch offsets **strictly below** it.
- **ISR** is the set of replicas the leader currently treats as caught up under a **replica-lag time bound** (commonly configured as `replica.lag.time.max.ms`). Membership is an operational lag SLA, not a proof of fsync.

A follower can remain in the ISR while its latest bytes still sit in page cache. If the leader’s LEO is 1,004,000 and a slow ISR member’s LEO is 1,003,940, consumers must not be served 1,003,940–1,003,999 yet. When that follower catches up, HW can move. When it exceeds the lag bound, it leaves the ISR and HW can move without it—**which shrinks the failure domain**. Pair that fact with `min.insync.replicas` in the [delivery lesson](/learn/kafka-delivery-and-failure); internals only tell you the ISR can shrink.

### Leader failover uses epochs, not “truncate to HW”

HW is a **read gate**, not a prediction that the next leader will delete everything above it.

On **clean** failover the controller elects a **current ISR member**. That replica typically **keeps** the log it already has, including some offsets that sat **above the previous leader’s HW**. Those offsets can become the new committed prefix as the new ISR catches up. Consumers still must not have read past the old HW: those bytes were never a committed prefix under the old leader.

When the **old leader** (or any replica whose log diverged) becomes a follower, it truncates a suffix using **leader-epoch end offsets** (KIP-101): it asks the current leader for the last offset of each epoch and cuts local bytes that disagree. That is more precise than “the new leader truncates to the old HW,” which can delete valid data the new leader still holds. **Unclean** election (a non-ISR replica) can still drop offsets producers treated as durable; that envelope stays in the [delivery lesson](/learn/kafka-delivery-and-failure).

### Page cache, fsync, and lag are operational, not magic durability

Brokers usually append through the **OS page cache**. A produce acknowledgement that waits for ISR copies typically means those replicas **accepted the batch into their logs**, not that every disk platter has completed `fsync`. Flush interval, filesystem barriers, volume type, and battery-backed controllers are **operator choices**.

**Planning assumption, not a measured guarantee:** if all ISR members lose power with dirty pages, acknowledged offsets can vanish even though producers received success. Replication across failure domains reduces that window; it does not delete physics. Treat `replica.lag.*` as “how long we still call you in sync,” not “how durable your last fetch was.”

### Controller: one metadata authority

Cluster membership, topic configuration, partition-to-leader assignment, and ISR snapshots live in **cluster metadata**. The required property is **one metadata/controller authority** at a time: brokers and clients must not invent a competing leader map.

KRaft implements that authority as a Raft-replicated metadata log. ZooKeeper plus a controller broker was an earlier implementation of the same property. Name the property first; name the store second. A controller failover loads that metadata and pauses **metadata changes** (new partitions, preferred-leader elections, ISR updates that need the controller) until a successor is active. Existing **partition** leaders keep serving the data plane on the last known assignment. Controller failover does **not** reassign every partition or fence every leader. Fence and reassignment happen when **partition** leadership changes. Stale client metadata yields `NOT_LEADER_OR_FOLLOWER`; recovery is a metadata refresh, not a second write path.

See [consensus and leader election](/learn/consensus-and-leader-election) for quorum safety; Kafka’s data plane is still per-partition leader replication, not one global Raft log of all transfers.

### Retention versus compaction

**Time and size retention** delete whole segments that are older than a horizon or that push the partition past a byte cap. An acknowledged offset is still gone after expiry. That is the replay bound, not a surprise.

**Log compaction** is a **different retention policy**: keep the latest record per key (and a tombstone long enough for consumers to see deletes). It is not a second database, not a lossless history, and not a ledger. Intermediate values disappear. If TokenX needs every transfer, do not compact the fact log; compact only a derived changelog that you can rebuild from facts.

Picture a bound ledger (the partition) whose current page is still being written (the active segment). Finished books go on the shelf (immutable segments). A clerk stamps “safe to read” only up to the page every on-duty copyist has photocopied (high-watermark versus log-end offset). Copyists who wander off the job are taken off the duty roster (ISR lag bound). A separate registrar keeps the list of who is clerk (controller metadata). Indexes are the table of contents: useful, rebuilt from the pages, never the original.

Compaction is the clerk throwing away yesterday’s drafts of the same account line and leaving the latest scribble. That saves shelf space. It is not a second vault.

The **active and sealed log segments** are the authoritative partition bytes until retention or compaction removes them. **Offset indexes** are derived and rebuildable. **Cluster metadata** (leaders, ISR snapshots, topic config) is a separate authority owned by the **single controller**; KRaft or ZooKeeper is how that log is stored. Replica fetch is **asynchronous**. The **high-watermark** is the exclusive consistency boundary for consumer reads: it trails the leader’s log-end offset until every current ISR member has the bytes. Dashed edges are failure and recovery: lag drops a follower from the ISR, controller-driven **partition** election replaces a dead data-plane leader, and crash recovery rebuilds indexes from log files. Controller process failover is metadata recovery, not a cluster-wide reassignment.

<RealExamples title="TokenX ledgers and hot ad campaigns">

**TokenX.** Partition transfer facts by `wallet_id` (or account) so debit/credit order for that wallet is the partition’s offset order. A celebrity wallet is a hot key: 400 of 2,000 transfers/s can land on one partition while others idle. Do not compact the fact log; you need history, compensating entries, and replay. A compacted **balance changelog** is a derived view you can rebuild. Cross-wallet settlement still needs an application protocol; two partitions are two logs. Delivery, retries, and sink idempotency remain in [Kafka delivery semantics and failure](/learn/kafka-delivery-and-failure).

**Ad Click Aggregator.** Keying by `campaign_id` preserves per-campaign append order and puts a viral campaign on one leader: **80,000 clicks/s × 800 B = 64 MB/s** into that partition before compression—enough to saturate a single replica path. Keying by `collector_id` spreads ingest and **defers** skew to the aggregator, which must then shuffle by campaign. Click facts need time/size retention for replay and dispute windows. Compaction belongs on **campaign config** (latest budget, latest pause flag), not on the click stream.

<InterviewTraps title="Internals slogans that fail at IC6">

1. **“Followers are synchronously mirrored, so LEO equals HW.”** Replica fetch is pull and can lag. Consumers are gated on the high-watermark.
2. **“In-sync means fsynced.”** ISR is a fetch-lag roster plus operator flush policy. Page cache is an operational durability assumption.
3. **“ZooKeeper (or KRaft) is what makes Kafka correct.”** The property is one metadata authority and per-partition ISR replication. The store is an implementation.
4. **“Compaction keeps a lossless latest-state database.”** Compaction drops prior values for a key. Tombstones expire. It is retention, not a second source of truth.
5. **“The offset index is the log.”** Indexes are derived. Recovery rebuilds them from segment bytes.
6. **“More partitions fix a hot wallet.”** They increase parallelism and **split** that wallet’s order unless you keep the key on one partition. See [partitioning](/learn/partitioning-vs-sharding-vs-aggregation).
7. **“Acks and internals are the same lesson.”** Internals are segments, HW, ISR, controller, retention. `acks=all`, `min.insync.replicas`, unclean election, and producer idempotence belong in [delivery semantics](/learn/kafka-delivery-and-failure).
8. **“Controller failover pauses all reads and writes.”** Metadata operations pause until a new controller loads the metadata log. Existing partition leaders usually keep serving. Fence and reassignment happen on **partition** leadership change, not because the controller process restarted. Stale metadata is a retry-and-refresh problem.
9. **“After failover the new leader truncates everything above the old HW.”** HW is why consumers must not read that suffix. The new ISR leader typically keeps its log. Diverged former leaders and followers truncate using **leader-epoch end offsets**, not a blind HW rewind.

</InterviewTraps>

<Tradeoffs title="Copy width, lag roster, retention, and fsync">

- **Larger ISR / higher replication factor** adds disk, network, and catch-up work, and buys more independent copies of log bytes. It does not change the fact that HW trails LEO.
- **Tight replica-lag time** drops slow followers quickly and keeps HW honest about “who is here,” but shrinks ISR under jitter and can collide with write availability if the delivery envelope demands a high minimum ISR.
- **Loose lag** keeps replicas “in sync” on paper while their LEO trails, delaying HW and hiding a copy that would not survive leader failover.
- **Per-message fsync** shrinks the power-loss window and adds latency plus disk queueing; **page-cache plus cross-rack ISR** is a common operational default and must be stated as such.
- **Long time/size retention** enables replay and incident debug at storage cost; **compaction** saves space for latest-per-key streams and destroys history. Using both (`compact,delete`) still expires old keys—it is not immortal state.
- **Campaign keys vs collector keys** trade per-entity order against ingest heat. Neither removes the need for a replay window on facts.

</Tradeoffs>

<InterviewAnswer>

“A Kafka partition is an ordered log of an active segment plus immutable older segments. Offset indexes are derived and rebuilt from log bytes after a crash. One leader takes appends; followers fetch. Log-end offset is local length; the high-watermark is the exclusive prefix every current in-sync replica has, and that is the consumer read gate—not a promise that the next leader will delete everything above it. Clean failover elects an ISR member that keeps its log; diverged former leaders truncate using leader-epoch end offsets. ISR is a replica-lag time roster, not an fsync certificate—page cache and flush policy are operational durability assumptions. Cluster metadata has one controller authority; KRaft versus ZooKeeper is the implementation. Controller process failover pauses metadata changes; it does not reassign every partition. Retention by time or size deletes segments; compaction is another retention policy that forgets a key’s past, not a second database. For TokenX I key by wallet and I do not compact the fact log. For ads I expect campaign skew. Acks, min ISR, unclean election, and producer idempotence sit on this machinery—I spell those out in the delivery envelope, not as slogans about exactly-once or immortal disks.”

</InterviewAnswer>
