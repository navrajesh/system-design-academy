<BigPicture title="The protocol is a contract, not a speed setting">

[Networking for system design](/learn/networking-for-system-design) placed HTTP on a deadline. [TCP, QUIC, and connection lifecycle](/learn/tcp-quic-and-connection-lifecycle) owns handshake and HOL. This lesson is **what the bytes mean**: REST/JSON, gRPC, GraphQL, streaming, status codes, idempotent methods versus POST with keys, payload evolution, and compression.

gRPC is HTTP/2 (or HTTP/3) with protobuf and deadlines. It is not automatically faster than JSON, and it does not make POST safe to retry. GraphQL is a query language over HTTP; it does not grant a client the right to mutate TokenX without the same uniqueness as REST.

**Authoritative effects** still live in the TokenX ledger and the Ad Click billed-fact log. HTTP 200 is a **statement about a response** that left the handler. If the append is asynchronous, 200 is a lie unless you named a different contract (accepted-for-processing).

</BigPicture>

<UnderTheHood title="Methods, status, evolution, then who may retry">

### Safety is a property of the effect, not the logo

- **GET, HEAD, PUT, DELETE** (when implemented as specified) are intended to be **idempotent** at the resource. PUT of the same body to the same URL should converge. TokenX **balances** as GET of a derived or replica view must label staleness. Spendable **debit** is not a GET.
- **POST /debits** is not idempotent unless `(tenant, transfer_id)` is in the body and unique in the **same** ledger transaction. 409 means that id already committed; return the stored result. Timeout means **UNKNOWN**—see [idempotency](/learn/idempotency-and-deduplication).
- **gRPC unary** is RPC-shaped HTTP. Deadlines map well. Automatic client retries in a stub are the same hazard as L7 retries in [load balancing](/learn/load-balancing-deep-dive): off unless the RPC is idempotent or keyed.
- **Streaming** (HTTP/2, gRPC bidi, SSE) is for long-lived flows. Deep WebSocket design sits in [real-time connections](/learn/real-time-connections). Do not commit money only on a stream without the same key as POST.
- **GraphQL mutations** that wrap a debit are still POSTs. Persisted queries do not fence uniqueness.

Status contract (illustrative, must match the product):

| Class | Meaning for TokenX debit | Meaning for Ad Click ingest |
| --- | --- | --- |
| 2xx | Ledger transaction committed (or 409-as-success replay) | Unique `click_id` durable on the log |
| 4xx (except 408/429) | Client will not succeed by blind retry | Malformed; do not retry the same bad body |
| 429 | Admission; Retry-After | Admission; uniqueness still required later |
| 5xx / 408 | UNKNOWN if the handler might have committed | UNKNOWN if the collector might have appended |

429 is [backpressure](/learn/backpressure-and-overload) and [rate limiting](/learn/rate-limiting), not a ledger.

### Evolution and compression

Additive protobuf fields and optional JSON keys are the safe default. Renaming a field or reusing a tag is a new API. TokenX must not interpret a missing `transfer_id` as “mint one on the server” for old clients—that forks identity.

<Calculation label="JSON versus protobuf plus gzip (illustrative)">

Ad Click ingest 50,000 POSTs/s, JSON body 800 B, gzip to 280 B, protobuf 180 B uncompressed.

JSON gzip CPU: assume 40 µs/req compress+decompress on a collector core → 50,000 × 40e-6 = **2.0** core-seconds per wall second (about two cores) before JSON parse. Protobuf at 10 µs/req → **0.5** cores. Bandwidth: gzip JSON 50k × 280 B = 14 MB/s; protobuf 9 MB/s.

gRPC wins this envelope on CPU and bytes **if** the schema is stable and clients can take a stub. It does not win if you still JSON-transcode at the edge, and it does not make retries safe. HTTP/2 HOL on TCP loss still applies; do not re-teach congestion here.

</Calculation>

<MentalModel title="A form number, not a courier brand">

REST, gRPC, and GraphQL are courier brands. The clerk cares whether the form number was seen. Sending the same form twice by a faster courier is still one stamp. Sending a new form because the first courier was “binary and multiplexed” is two stamps.

Retain: **status codes name uncertainty, keys name identity, evolution is additive, and gRPC is not a commit.**

</MentalModel>

**Authoritative:** ledger unique `(tenant, transfer_id)`; billed log `click_id`. **Derived:** transcoded JSON, protobuf views, GraphQL graphs, gzip buffers, HTTP status if it left the process after a crash. Solid edges are keyed calls that commit. Dashed edges are unkeyed proxy retry, ACK-before-append, and dashboard reads. <RealExamples title="TokenX 409 replay; Ad Click ACK after append">

**TokenX.** Public JSON POST and internal gRPC unary share one handler. Both require `transfer_id`. Transcoding is not a second ledger. OpenAPI compatibility: new optional fields only. Compression on the receipt is optional; do not gzip-bomb the remaining 50 ms of deadline with a portfolio blob on the debit RPC.

**Ad Click.** HTTP POST `/clicks` with `click_id`. 2xx means the log append with uniqueness succeeded. An asynchronous Kafka produce of **debug** fields may fail; that does not retract the billed 2xx. If you return 202 Accepted before append, the contract is **not billed yet**—and finance must not use 202 counts. Prefer 200 after durability for billed ingest.

<InterviewTraps title="API slogans">

- **“gRPC is always faster.”** Measure. Transcoding and HOL can erase the win.
- **“REST is CRUD so POST is fine to retry.”** POST is not idempotent by default.
- **“4xx means never retry; 5xx means always retry.”** 409 is a stored success. 500 after possible commit is UNKNOWN.
- **“Protobuf is schema-safe forever.”** Tag reuse and required-field adds break old binaries.
- **“HTTP 200 means the click is billed”** when append is async—only if you defined 200 that way, which you should not.
- **“GraphQL solves overfetch and therefore consistency.”** Overfetch is payload shape, not a ledger.

</InterviewTraps>

<Tradeoffs title="Ergonomics, evolution, and retry surface">

- **JSON/REST versus gRPC:** debugability and browser clients versus stubs, deadlines, and compact codecs.
- **One resource POST versus many fine RPCs:** chattiness versus blast radius of a fat mutation.
- **Compression on versus off:** WAN bytes versus CPU and tail latency ([batching and compression](/learn/batching-and-compression)).
- **Strict 200-after-commit versus 202:** honesty versus apparent availability.

Money chooses keyed POST/unary and honest UNKNOWN over a prettier stub.

</Tradeoffs>

<InterviewAnswer>

“I pick REST or gRPC from clients, schema evolution, and codec cost—not from a slogan that binary is always faster. TokenX POST /debits is not idempotent without transfer_id in the same ledger transaction; 200 and 409 both mean the stored receipt, and a timeout is UNKNOWN. I disable unkeyed retries at stub and proxy. Ad Click 2xx means unique click_id is on the billed log, not that a GraphQL layer enqueued RAM. Compression and HTTP/2 multiplexing are performance knobs with CPU and HOL costs taught in neighboring lessons. Additive schema changes only. The courier brand never replaces the form number.”

</InterviewAnswer>
