<BigPicture title="Fast components do not guarantee a fast system">

Latency is time per request; throughput is completed work per unit time. As utilization approaches capacity, queues grow and tail latency can explode even when average service time stays constant.

Production SLOs should use percentiles such as p95 and p99. The slowest dependency often dominates user experience through fan-out.

</BigPicture>

<UnderTheHood title="Measure waiting separately from work">

Instrument queue time, service time, and downstream time. A 20 ms database query may still yield a 900 ms response if it waits behind an unbounded connection pool.

Little's Law states <code>L = λW</code>: average work in a defined system equals arrival rate times average time in that same system. At 2,000 requests per second and 200 ms average **end-to-end** latency, about 400 requests are in flight across the whole request path. That number does not tell us how many database connections are busy.

<Calculation label="Concurrency estimate">
Whole path: L = 2,000 requests/s × 0.2 s = 400 requests in flight

If 65% reach the DB: λDB = 2,000 × 0.65 = 1,300 DB operations/s

If a DB operation holds a connection for 20 ms: LDB = 1,300 × 0.020 = 26 busy connections on average

A 50-connection pool is therefore about 52% utilized on average—not 400 ÷ 50.
</Calculation>

Database pool sizing must use the arrival rate **to the database** and the time a request actually holds a connection. It also needs headroom for p95 service time, transactions that issue multiple statements, and uneven bursts. Averages alone can hide a saturated pool.

<MentalModel title="Utilization buys efficiency by spending latency">

Think of a grocery checkout: arrival rate is shoppers entering, service time is time at a register, and concurrency is shoppers currently in the store or checkout system. Counting everyone in the store does not tell you how many registers are occupied. Define the boundary before applying the formula.

Keep deliberate headroom. Bound every queue. When overload arrives, reject low-priority work quickly, shed optional features, and propagate backpressure rather than converting a short spike into minutes of stale work.

</MentalModel>

<ArchitectureDiagram title="Performance controls and ownership boundaries" chart={"flowchart LR\n  C[Clients] -->|deadline + idempotency key| A[Admission control]\n  A -->|accepted| Q[Bounded app queue]\n  A -->|overload| R[429 + retry-after]\n  Q --> W[Stateless worker pool]\n  W -->|acquire with timeout| P[Bounded DB connection pool]\n  P --> D[(Authoritative DB)]\n  D -. slow query / lock wait .-> P\n  W --> M[Queue, service, saturation metrics]\n  C -. capped retry with jitter .-> A"}>

The application owns admission and its bounded queue; the connection pool owns scarce database concurrency; the database owns durable state. Deadlines and cancellation must propagate across both queues so abandoned work does not continue consuming capacity.

</ArchitectureDiagram>

<RealExamples title="Fan-out and batch processing">

A profile page calling 20 services has more chances to encounter one p99 response. Use deadlines, parallel requests, cached fallbacks, and partial responses. In batch jobs, larger batches improve throughput by amortizing overhead but increase per-item wait and retry blast radius.

<InterviewTraps title="Performance errors to avoid">

- Reporting only average latency.
- Increasing timeouts without reducing overload.
- Using an unbounded queue as a shock absorber.
- Assuming more threads help CPU-bound work.
- Omitting the concurrency implied by latency and request rate.

</InterviewTraps>

<Tradeoffs title="Headroom is reliability capacity">

Lower utilization costs more but contains queues and failures. Batching raises throughput but delays the oldest item. Hedged requests reduce tail latency but add load; issue them only after a delay and within a budget.

</Tradeoffs>

<InterviewAnswer>

“I establish latency percentiles and throughput targets, then decompose queue, service, and dependency time. Little's Law gives the expected concurrency. I keep headroom, bound queues, use deadlines and cancellation, and shed work before saturation causes a retry storm. I optimize the bottleneck shown by profiles and saturation metrics, not whichever component looks easiest to scale.”

</InterviewAnswer>
