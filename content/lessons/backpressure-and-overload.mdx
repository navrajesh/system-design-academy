<BigPicture title="Overload is a queueing problem you either bound or you donate latency">

When arrivals exceed service rate, **something** stores the difference: a client retrying, an unbounded LinkedBlockingQueue, a Kafka producer `buffer.memory`, consumer fetch, or the caller’s thread. [Latency, throughput, and queues](/learn/latency-throughput-and-queues) is the math: Little’s Law, utilization, and why tails explode. This lesson is the **mechanism**: **push versus pull** flow control, **bounded buffers**, **load shed (429) versus queue**, **priority and fairness**, Kafka **producer buffer + `max.block.ms`**, **consumer pause that still `poll()`s**, and **rate limits as admission**.

[Graceful degradation](/learn/graceful-degradation) owns **what you stop first** (circuit breakers, bulkheads, fail-closed money, sampled dashboards). Do not re-derive breaker state machines here. Use that lesson for isolate-and-skip policy. Use this one for **how bytes stop moving** when a buffer is full.

Authoritative TokenX money still commits only in the ledger plus `(tenant, transfer_id)`. Authoritative Ad Click invoices still live on the billed-fact log. Rate limiting a client to 100 req/s does **not** make those writes unique. Unbounded queues convert an SLO into a latency disaster: admitted work waits until deadlines expire, then retries refill the same queue.

</BigPicture>

<UnderTheHood title="Pull when you can, bound when you must, shed when the bound is full">

### Push versus pull

**Push:** the producer sends whenever it has data. The consumer’s receive buffer, thread pool, or disk is the shock absorber. TCP windowing is push with a bound (the receive window). Kafka clients that `send()` into `buffer.memory` are push into a local bound. An HTTP client that ignores 429 and keeps POSTing is unbounded push.

**Pull:** the consumer asks for the next unit when it has capacity. Kafka fetch is pull: the member `poll()`s, the broker serves up to `max.partition.fetch.bytes`. A TokenX worker that only `take()`s from a bounded queue is pull. Pull does not magically cap the **log**: if producers keep appending, lag still grows until **produce** is shed.

Flow control is “who is allowed to send the next byte.” It is not a commit. A blocked `send()` is **not** `acks=all`. See [Kafka delivery and failure](/learn/kafka-delivery-and-failure) for the ACK boundary.

### Bounded queues versus unbounded (apply the latency lesson; do not re-derive it)

Little’s Law still holds at whatever boundary you name. If you **do not** bound the queue, W grows without an SLO: surplus arrivals accumulate forever (until OOM). If you bound it to *K* permits, admitted W is capped and **excess must be rejected or the sender must block with a timeout**.

Illustrative: TokenX transfer API sustainable μ = 2,000 commits/s (ledger hold 12 ms, enough owners). Offered λ = 3,000/s for 30 s. Surplus = 1,000/s. Unbounded queue depth after 30 s ≈ **30,000** transfers; wait for the last admitted ≈ 30,000 / 2,000 = **15 s** and still growing if the spike continues. A bound of 400 in-flight (from the latency lesson’s L = λW headroom) plus **429** keeps admitted p99 near service time; 1,000/s get a fast no.

That is the same surplus-and-wait story as the queues lesson. The new rule: **name K, name the reject, name who is exempt.**

<Calculation label="Bound K, then 429 the surplus">

Planning assumptions (illustrative): TokenX 2,000 sustainable commits/s; target admitted W = 200 ms → K ≈ 2,000 × 0.2 = 400 in-flight. Kafka producer `buffer.memory` = 32 MiB, billed fact 800 B encoded → ~42,000 records in the client before block. `max.block.ms` = 60,000 ms would hold an API thread for a minute; `max.block.ms` = 100 ms plus a throw is admission.

Ad Click: billed 20,000 facts/s, debug 40,000/s, apply 22,000/s. If you queue both classes together, surplus 38,000/s. After 10 s the mix queue holds ~380,000 records and billed facts sit behind debug. Priority isolation: cap debug in-flight at 2,000; 429 or drop debug first; billed keeps leftover apply.

Autoscaling does not replace the bound: [Autoscaling and capacity planning](/learn/autoscaling-and-capacity-planning) adds replicas **after** a signal. During the warm-up window the queue still needs a K and a 429.

</Calculation>

### Load shed 429 versus queue

| Move | What the caller sees | What capacity does | Honest use |
| --- | --- | --- | --- |
| Queue (bounded) | Latency up to the bound | Smooths **short** bursts | Burst shorter than K / surplus |
| 429 / 503 + Retry-After | Fast failure | Protects admitted p99 | Surplus longer than the bound, or low-priority class |
| Block `send()` until `max.block.ms` | Caller thread stuck | Converts broker stall into API latency | Only with a **short** timeout, then shed |

Queueing a TokenX debit for 15 s while the client already timed out at 200 ms is orphan production. Prefer 429 on **debug** and on **excess transfers above K**. Do not 429 uniqueness checks to “save the ledger”—that is an integrity shed, forbidden the same way degradation fail-closed money.

HTTP 429 is **proven non-accept** in the retries lesson: the server did not apply the debit. Timeout while queued is **UNKNOWN** if the handler might have started. Prefer reject **before** the uniqueness insert.

### Priority and fairness

**Priority** is which class is admitted when K is almost full. **Fairness** is whether one tenant, partition, or debug firehose can consume K alone.

TokenX: **transfer / debit / credit** outranks metadata reads, which outrank **debug traces**. Under overload, shed debug first, then metadata, then delay extra transfers with 429—not the reverse. A noisy tenant still needs a **per-key or per-tenant** token bucket so celebrity account A cannot occupy every ledger permit (the row lock still serializes A; fairness stops A’s debug plus everyone else’s transfers sharing one HTTP pool).

Ad Click: **billed clicks** outrank **debug clicks** and verbose payloads. Fairness: one viral `campaign_id` must not fill the collector queue so other campaigns’ billed facts 429. Isolate permits per class (and per hot key if needed). That isolation is a **queue policy**. Breaker open/closed lives in the degradation lesson.

### Kafka: producer buffer, `max.block.ms`, pause still needs poll

- **`buffer.memory`:** local push bound. Full buffer → `send()` **blocks** up to **`max.block.ms`**, then throws. The throw is **not** a broker ACK. The record may be nowhere.
- **`max.block.ms` too large:** API threads become the queue. Same disaster as unbounded in-process queues, with extra steps.
- **Consumer `pause()`:** stops **fetch** for those partitions. You must still **`poll()`** so `max.poll.interval.ms` does not expire. Heartbeats without poll still look dead to the processing-loop detector—same trap as [Consumer groups and rebalancing](/learn/consumer-groups-and-rebalancing). Pause is backpressure on **consume**. It does **not** drop already-acked produce and does **not** cap lag unless **producers** shed.

### Rate limits are admission, not correctness

A token bucket (100 req/s/key, burst 20) **shapes offered load**. It does not:

- insert `(tenant, transfer_id)`
- fsync billed facts
- order account mutations
- provide exactly-once processing
- replace a unique constraint if the client retries with a new id

Two TokenX clients can each be under their 100 req/s cap and still double-apply if they mint different `transfer_id`s for one user click. Rate limits **protect the pool**. Idempotency **protects the ledger**. You need both.

<MentalModel title="A loading dock with a painted line and a bouncer">

Pull is the forklift driver asking for the next pallet when there is floor space. Push is the truck dumping pallets until the warehouse collapses. The **painted line** is K (bounded buffer). The **bouncer** is 429 / `max.block.ms` timeout: people at the door get a fast no so the people inside still ship. **Priority** lets ambulances (TokenX transfers, billed clicks) past tourists (debug). **Fairness** is one noisy truck not occupying every dock. Kafka’s producer buffer is a **small warehouse with a clock**; when the clock fires, you refuse—you do not stamp “delivered.” Pause is telling the forklift to stop fetching that aisle while still **checking in** with the coordinator (`poll`).

Retain: **bound K, pull if you can, 429 surplus, rank money and billed facts above debug, treat rate limits as doors not ledgers, and keep polling while paused.**

</MentalModel>

**Authoritative state:** TokenX ledger plus uniqueness, and the Ad Click billed-fact **log** until retention plus the billed sink. **Derived:** debug topics, dashboards, group lag, producer buffer contents (unacked). **Consistency boundary:** money is committed only at the ledger transaction; Kafka ACK is a different envelope ([Kafka delivery and failure](/learn/kafka-delivery-and-failure)). Rate limiter and priority gate are **admission**, not that boundary. Solid edges are admitted push-into-bound and pull-from-log. Dashed edges are 429, debug drop, `max.block.ms` produce shed, and pause (async stop-fetch while poll continues). Recovery: Retry-After with jitter on 429, drain the bounded queue, unpause when leftover apply rate is positive, never “recover” by ACKing money from a full buffer.

<RealExamples title="TokenX 429s debug before money waits; ads pause debug fetch and keep billed pull">

**TokenX.** Mesh and API share a concurrency bound K sized from admitted λ × target W (example: 2,000/s × 0.2 s = 400). **Transfer** class always competes for ledger permits; **debug** traces 429 at 80% of K. Per-tenant buckets stop one integration test from occupying K. `send()` of analytics uses a **separate** buffer and `max.block.ms` ≈ 100 ms; a throw skips analytics (degradation policy) and **must not** rewind the ledger. Rate limit 50 transfers/s/merchant is so a bug does not hot-loop the primary; the merchant still sends one `transfer_id` per user action. Fairness does not add a second writer on celebrity account A—the row remains one cashier.

**Ad Click Aggregator.** Collectors use a bounded in-memory batch (for example 500 facts or 20 ms linger) then `send()`. If the buffer fills, billed path fails the SDK with 429/503 **after** not appending; the SDK retries the **same** `click_id`. Debug path drops. Consumers **pull** billed partitions first. When debug lag exceeds 100,000 records they `pause()` debug, **continue `poll()`**, and leave billed fetching. Pause does not stop collector produce—collectors must shed debug. Extra consumer members above partition count stay idle ([Consumer groups and rebalancing](/learn/consumer-groups-and-rebalancing)); they are not a flow-control valve.

<InterviewTraps title="Overload slogans that fail in staff+ interviews">

- **“The queue is our shock absorber.”** Unbounded queues absorb until OOM or until every deadline is already dead. Bound K.
- **“Pull means the log cannot grow.”** Pull caps **fetch**. Produce still appends. Shed or 429 the producer.
- **“429 means we lost the debit.”** 429 before the uniqueness insert is proven non-accept. A timeout after insert is UNKNOWN—same `transfer_id`.
- **“max.block.ms is durability.”** It is how long **you** wait for local buffer space. `acks` is the broker envelope.
- **“We paused, so those records were dropped.”** Pause stops fetch. Previously acked records remain until retention.
- **“Paused consumers do not need poll; heartbeats are enough.”** `max.poll.interval.ms` is the processing-loop detector.
- **“Rate limit = exactly-once.”** Admission is not a unique constraint.
- **“FIFO is fair.”** FIFO lets debug starve transfers and one campaign starve others. Name classes and tenant weights.
- **“HPA will catch the spike.”** Warm-up is not zero. K and 429 still apply during scale-out ([Autoscaling and capacity planning](/learn/autoscaling-and-capacity-planning)).
- **“Open the circuit instead of bounding the queue.”** Breakers are the degradation lesson’s **dependency** policy. You still need K on the path that remains open.

</InterviewTraps>

<Tradeoffs title="What you spend to keep W finite">

- **429 versus queue:** 429 spends availability of the **excess** class to buy latency for the admitted class. Queue spends latency to buy burst absorption up to K.
- **Push versus pull:** push is simple and overruns the consumer; pull needs a live poll loop and still needs produce-side shed.
- **Short `max.block.ms` versus long:** short throws sooner and can storm retries unless you 429 with Retry-After; long turns API threads into the buffer.
- **Priority versus utilization:** strict transfer-first can idle debug forever (starvation). Weighted fairness spends some transfer latency to give debug a trickle.
- **Per-tenant buckets versus global K:** tenant buckets stop noisy neighbors and add state and mis-configuration. Global K is simpler and unfair under skew.
- **Rate limit tightness versus headroom:** a tight bucket protects the primary and rejects healthy bursts; a loose bucket is admission theater.

Correctness of TokenX balances and billed-click identity is not a flow-control knob. Completeness of debug and dashboards is.

</Tradeoffs>

<InterviewAnswer>

“I treat overload as surplus arrivals that must sit in a named, bounded place or be rejected. Pull when the consumer can ask—Kafka fetch, worker take—and remember pull does not cap the log. Push needs a bound: app queue depth K from admitted lambda times target W, and Kafka buffer.memory with a short max.block.ms so send() is admission, not a one-minute thread queue and not acks=all. If surplus would break the SLO I 429 or 503 with Retry-After, especially debug; I do not grow an unbounded FIFO until clients time out. Priority is TokenX transfers over debug, billed clicks over debug clicks, with per-tenant fairness so one firehose cannot occupy K. Pause stops fetch; I still poll so max.poll.interval.ms does not expire, and I shed produce or lag keeps growing. Rate limits are doors, not unique constraints: money still fails closed on (tenant, transfer_id), billed facts still need click_id. Circuit breakers and bulkhead policy live in graceful degradation; autoscaling cannot replace the bound during warm-up. I never call a full buffer exactly-once or lossless.”

</InterviewAnswer>
