<BigPicture title="A guarantee is a falsifiable claim">

Distributed correctness cannot be established by green health checks or a happy-path integration test. A useful test states a model, drives concurrent operations, records a complete enough history, injects realistic faults, and checks whether any legal execution explains the observations. It also verifies recovery after the fault stops.

Linearizability checking asks whether completed operations can be placed at single points between invocation and response while respecting real-time order and the object's sequential specification. Domain invariant checking asks questions such as “did TokenX conserve value?” These are related but distinct: a system may violate linearizability without losing money, or conserve total money while double-charging one account.

</BigPicture>

<UnderTheHood title="Generate, record, perturb, check, recover">

Define the object model before load. A register supports read and write; a set supports add, remove, and contains; a transfer model includes balances, idempotency, and conservation. Record unique operation ID, client, invocation time, completion time, input, output, error class, and server-observed version when available. Client clocks help bound real-time order but must not be treated as perfectly synchronized; a centralized harness clock or interval uncertainty improves evidence.

### Linearizability search

The checker builds a partial order: if operation A completed before B began, A must precede B; overlapping operations may be ordered either way. It searches for a sequential history allowed by the model and matching observed outputs. Search can be expensive, so partition independent keys, keep histories bounded, and minimize failures to a small counterexample.

An invocation with no response is **unknown**, not automatically failed. It may be linearized or omitted depending on whether the server could have committed. Later reads and idempotency lookup can constrain its outcome. Losing client history records can make an invalid execution appear legal, so the harness needs durable, append-only evidence.

### Domain invariants and reconciliation

For TokenX, initialize 10,000 accounts with 1,000 units each: total supply is 10 million units. After concurrent transfers, successful idempotent retries, leader changes, and partitions, verify total debits equal credits, no unauthorized negative available balance occurred, each key has one result, and account sequences contain no unexplained duplicates or gaps. A zero total alone is insufficient: one account could lose funds while another gains them wrongly.

For ad clicks, inject duplicate delivery, late events, consumer rebalance, state loss, and replay. Compare aggregate versions with a deterministic batch computation from raw event IDs. Define accepted lateness and dedupe horizons so the oracle matches the product contract.

Faults should resemble actual assumptions: bidirectional and asymmetric partitions, process kill and pause, disk-full or fsync errors, clock skew, stale DNS, and dependency delay. Avoid destructive production experiments unless scope, rollback, and safety controls are explicit.

</UnderTheHood>

<MentalModel title="A crash-test laboratory with a court transcript">

The workload is the vehicle, injected faults are controlled collisions, and the history is a timestamped transcript. The checker does not ask whether the dashboard stayed green; it asks whether any allowed sequence can explain every recorded action and result.

Retain: specify the model, preserve evidence, inject one understood fault family, check safety, then prove the system recovers.

The system under test owns application state; the harness owns an independent history and fault schedule. Checkers consume evidence but must not mutate the system. Recovery verification is a first-class phase. The history store must survive harness crashes, or missing operations can invalidate the analysis.

<RealExamples title="Testing the guarantee users actually depend on">

**TokenX transfer register.** Multiple clients transfer randomized amounts under stable keys while the harness kills leaders, delays acknowledgements, and partitions replicas. The checker combines strict-serializable account behavior with conservation, nonnegative authorization, one result per key, and replay-safe recovery.

**Ad Click Aggregator.** Generate events with a known stable ID set and controlled event-time distribution. Inject duplicates, reorderings, late delivery, consumer rebalances, and checkpoint loss. Compare live and replayed aggregate versions to an offline oracle under the declared watermark and correction policy.

**Lock service.** Pause a holder past expiry, grant a later token, then release the old write. The test succeeds only if the protected resource—not merely the lock service—rejects the stale token.

<InterviewTraps title="Tests that create confidence without evidence">

1. **“Chaos testing proves correctness.”** Fault injection without a formal model or invariant oracle measures symptoms, not the guarantee.
2. **“A timeout is a failure.”** It is an unknown outcome and must remain optional in the history until evidence constrains it.
3. **“Linearizable means serializable.”** The checker model must match object operations or multi-object transactions and their real-time contract.
4. **“No anomaly in one run proves safety.”** Testing finds counterexamples; it cannot prove all executions correct.
5. **“Kill random pods.”** Target the system's assumptions: quorum links, stale leaders, fsync, clocks, membership, and recovery paths.
6. **“Stop when the partition heals.”** Verify convergence, resumed progress, cleaned prepared state, and restored redundancy.
7. **“Production chaos first.”** Start with deterministic lab tests and bounded blast radius; protect customer state and external effects.

</InterviewTraps>

<Tradeoffs title="Fidelity, search cost, and operational safety">

- Model checking gives precise counterexamples but state space grows quickly; narrow objects and independent-key partitioning help.
- End-to-end tests include real drivers and networks but make timing evidence noisier than in-process model tests.
- Deterministic fault schedules improve reproducibility; randomized schedules explore more interleavings.
- Rich server instrumentation constrains unknowns but risks coupling the oracle to the implementation.
- Production experiments reveal environmental behavior but require strict blast-radius, abort, and data-protection controls.

</Tradeoffs>

<InterviewAnswer>

“I turn a guarantee into a model and an independent history. The harness records invocation, completion, unique ID, result, and unknown timeouts, while a controlled nemesis injects partitions, pauses, clock faults, and acknowledgement loss. A linearizability checker searches for a legal real-time-respecting sequence; separate domain checks cover conservation, nonnegative balances, and one result per idempotency key.

I validate the harness against known-good and deliberately broken systems, minimize counterexamples, and continue after healing to verify convergence and liveness. Tests find violations rather than prove all executions safe.
