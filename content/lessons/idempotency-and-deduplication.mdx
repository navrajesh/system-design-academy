<BigPicture title="Retries are safe only when identity survives uncertainty">

Networks turn success into ambiguity: a server can commit and lose the response, so a client timeout does not mean failure. Idempotency makes repeating the same logical command return the same outcome without repeating its effect. Deduplication detects an identity seen before; it is useful only when the identity, scope, atomic boundary, and retention window match the business operation.

TokenX uses a tenant-scoped idempotency key for transfer creation and stores the request fingerprint plus result in the same transaction as the ledger mutation. The Ad Click Aggregator uses stable click IDs within a declared dedupe horizon, while replayable aggregate outputs use deterministic keys and versions.

</BigPicture>

<UnderTheHood title="Claim and effect must be one decision">

The unsafe pattern is “check key, perform effect, then store key.” Two requests can both pass the check, or the process can crash after the effect but before recording it. Treat **local atomic commands** and **long-running workflows** as different patterns. An uncommitted intermediate claim is not durable progress: a crash rolls it back, and a duplicate must not observe it as `IN_PROGRESS` or `SUCCEEDED`.

### Two different idempotency patterns

**Local atomic idempotency** covers a command whose effect fits in one database transaction. Insert the unique `(tenant, operation, key)` row, apply the mutation, and commit `SUCCEEDED` (or a classified terminal failure) together. After that commit there is no durable `IN_PROGRESS` for the local effect. A concurrent duplicate loses the unique insert and replays the stored result. Do not teach “leave IN_PROGRESS, then mutate, then succeed” for this case: a crash between those steps is the original race, and other requests must not treat an uncommitted row as progress.

**Recoverable workflow idempotency** covers work that cannot finish in one local transaction, such as a provider call or saga step. Persist `IN_PROGRESS` with the request fingerprint, owner identity, and a lease or fencing epoch **before** the remote call. That claim is durable only after its insert commits. A duplicate that sees committed `IN_PROGRESS` should wait, return `202` with the operation URL, or attempt takeover. Takeover is allowed only after the new owner fences the old epoch and queries the remote effect; it must not assume `IN_PROGRESS` means the side effect never happened.

Do not cache every transient 500 forever. Persist a canonical hash of semantically relevant parameters; the same key with a different amount or destination is a conflict.

The idempotency result should include the stable resource ID and enough response data to preserve API semantics. Large bodies may be regenerated from the authoritative resource if versioned. Scope keys by tenant and endpoint so two customers choosing `123` do not collide.

### Retention is part of correctness

If clients retry for 24 hours, queues replay for seven days, and offline devices can reconnect after 30 days, a one-hour dedupe TTL is not a safety guarantee. Retention must cover the longest accepted duplicate horizon or old requests must be rejected by protocol version/expiry.

At 2,000 commands/s and seven-day retention, there are `2,000 × 604,800 ≈ 1.21 billion` records. At 120 bytes logical each, that is about 145 GB before indexes and replicas. Partition expiration by time, archive audit evidence if required, and keep the primary lookup bounded. A Bloom filter can reduce negative storage reads but cannot be the authority because false positives would reject valid commands and false-negative behavior after reset would admit duplicates.

### Consumer deduplication

For an external database consumer, commit an inbox event ID and local side effect in one database transaction. Commit the broker offset afterward. A crash before offset commit causes redelivery; inbox uniqueness makes it a no-op. Kafka transaction guarantees do not automatically include an unrelated database or payment provider.

<RealExamples title="Identity at each side-effect boundary">

**TokenX transfer.** Key scope is `(tenant, create-transfer, key)`. The fingerprint includes source, destination, asset, amount, and semantic options. A reused key with a different amount returns conflict. The stored result points to one immutable transfer ID.

**Ad Click Aggregator.** Edge-generated click IDs dedupe transport retries. The service declares a seven-day online window; archival reprocessing uses a batch namespace plus deterministic event identity so it cannot collide with live state. Aggregate updates use `(campaign, window, version)` replacement, not blind increments on replay.

**Payment provider.** The dispatcher first persists one provider command, then calls with that command ID as the provider's idempotency key. A timeout is resolved by replay or provider lookup. Local dedupe without provider support cannot prove the remote charge happened once.

<InterviewTraps title="Exactly-once claims with a missing boundary">

1. **“The endpoint is idempotent because it uses PUT.”** HTTP method naming does not implement atomic identity or outcome replay.
2. **“Store the key after success.”** A crash between effect and record leaves the exact ambiguity idempotency must solve.
3. **“Leave IN_PROGRESS, then mutate locally, then succeed.”** For a local command that is one transaction: an uncommitted claim is not progress, and splitting the steps reintroduces the race. Use `IN_PROGRESS` only for work that outlives one commit.
4. **“Deduplicate by payload.”** Two intentional equal purchases are distinct commands; identity must come from the caller or workflow.
5. **“Keep keys for an hour.”** Derive retention from retry, queue, offline, and archival replay horizons.
6. **“Kafka exactly-once covers our database.”** External state needs an inbox or a proven transactional connector boundary.
7. **“Cache the 500 response.”** Distinguish terminal business failures from transient infrastructure failures and unknown outcomes.
8. **“Bloom filter means seen.”** Probabilistic membership cannot be the authoritative rejection decision for money.
9. **“IN_PROGRESS means the provider was never called.”** After a timeout the remote effect is unknown; takeover must query or replay the same command ID.

</InterviewTraps>

<Tradeoffs title="Safety window versus state cost">

- Long retention handles delayed retries but creates large hot indexes and privacy/retention obligations.
- Storing full responses gives exact replay but costs space; storing resource references requires stable versioned reads.
- Waiting on workflow `IN_PROGRESS` reduces duplicate remote calls but can tie up requests; returning an operation URL makes progress explicit. Local atomic commands should not linger in `IN_PROGRESS` after commit.
- Client-generated keys preserve identity across network failure, but clients need correct scoping and persistence.
- Natural business keys can be ideal when truly unique; forcing unrelated operations into one key can reject valid repeats.

</Tradeoffs>

<InterviewAnswer>

“Idempotency closes the unknown-outcome window with stable identity. For a local TokenX transfer I scope the key by tenant and operation, hash the semantic request, and commit key, ledger mutation, SUCCEEDED result, and outbox intent together—no durable IN_PROGRESS after that commit. An uncommitted claim is not progress. For a provider call I first commit IN_PROGRESS with owner and epoch, then call with that command ID; duplicates wait or take over only after fencing and a remote lookup.

Every later boundary needs its own identity: outbox event ID, transactional consumer inbox, and provider idempotency key. Retention must cover the longest supported retry or replay horizon; otherwise old duplicates become new commands. See [transactions across boundaries](/learn/transactions-across-boundaries), [Kafka delivery](/learn/kafka-delivery-and-failure), and [distributed transactions](/learn/distributed-transactions).”

</InterviewAnswer>
