<BigPicture title="A lock is safe only where stale holders are rejected">

A distributed lock service can grant one owner at a time according to its own state. It cannot pause a process, retract a message already in flight, or force an external database to ignore an expired owner. Garbage-collection pauses, network partitions, scheduler suspension, and delayed packets can let an old holder continue after a lease expires.

The usual defense is a fencing token: every successful acquisition receives a monotonically increasing epoch, and the protected resource rejects operations with a token lower than the highest it has accepted. Without enforcement at the resource, a lease is coordination advice—not proof of exclusive side effects.

</BigPicture>

<UnderTheHood title="Acquire, renew, fence, and stop">

A lease is time-bounded ownership recorded by a linearizable authority. The client acquires resource `R`, owner identity, expiry, and token 42. It renews before expiry while still authorized. The client must stop work if renewal cannot be confirmed; it cannot extend the lease from its local clock alone.

### Time assumptions

Lease safety depends on the authority's time semantics and client behavior. A client may use a monotonic local clock to decide to stop early, subtracting clock-drift and network uncertainty from usable duration. It must never conclude that the server-side lease remains valid merely because its wall clock has not reached an expiry timestamp.

For a 30-second lease, 10-second renewal interval, 2-second worst observed pause, and 1-second network budget, a client has substantial operating margin. But these are measured assumptions, not correctness proofs. A 40-second stop-the-world pause can exceed them; fencing still protects the resource after the pause.

### Lock granularity and contention

One global lock serializes unrelated work and becomes an availability bottleneck. Lock by stable resource ID, keep critical sections small, and avoid remote calls while holding database locks. If 500 jobs/s each hold a lock for 200 ms, Little's Law gives about 100 concurrent held locks across distinct keys. If all jobs use one key, capacity is at most five jobs/s regardless of worker count.

Use atomic compare-and-set, uniqueness constraints, work queues with ownership epochs, or idempotent writes when they express the actual invariant more directly. A lock around “check then insert” is usually weaker than a database unique constraint on the insert.

</UnderTheHood>

<RealExamples title="Locking only the actual shared resource">

**TokenX settlement batch.** A scheduler lease chooses one active batch coordinator, but settlement rows use a unique batch ID and the database rejects stale fencing tokens. Provider submissions use an idempotency key because the provider may not understand the internal lease epoch.

**Ad Click compaction.** Workers lease `(campaign, hour)` segments. Output is written under an immutable generation key, and a metadata compare-and-set publishes only the newest token. A stale worker may finish expensive computation, but cannot replace the current manifest.

**When no lock is better.** Parallel consumers inserting the same transfer receipt should rely on a unique event ID plus an atomic upsert. This survives retries without depending on a lease being continuously held.

<InterviewTraps title="Locks that do not protect the resource">

1. **“The TTL prevents two owners.”** It permits reassignment; it does not stop a paused old process.
2. **“Use NTP-synchronized clocks.”** Clock synchronization reduces error but does not eliminate pauses, message delay, or clock steps.
3. **“The lock server says I own it.”** The mutation destination must enforce the token atomically.
4. **“Renew after expiry if no one else acquired.”** The old epoch is over; reacquire a new token and revalidate work.
5. **“Lock the whole tenant.”** Calculate contention and choose the smallest key that contains the invariant.
6. **“A distributed lock makes a remote API atomic.”** Use provider idempotency and durable outcome reconciliation.
7. **“Release in finally.”** Release is useful but cannot be required for safety because crashed clients never run it.

</InterviewTraps>

<Tradeoffs title="Mutual exclusion versus availability and simplicity">

- Short leases recover quickly from crashes but renew often and are sensitive to pauses; long leases delay reassignment.
- Fencing provides robust stale-holder protection but requires every protected resource to compare generations.
- Coarse locks are simpler but destroy parallelism and expand failure blast radius.
- Fine locks improve concurrency but increase acquisition volume, ordering complexity, and deadlock risk.
- Idempotent or commutative operations often avoid locks entirely, but are inappropriate when the invariant truly requires one exclusive decision.

</Tradeoffs>

<InterviewAnswer>

“A lease is not enough because an old holder can pause and resume after expiry. I acquire from a linearizable authority, stop work when renewal cannot be confirmed, and attach a monotonically increasing fencing token to every protected mutation. The resource atomically rejects tokens below its highest accepted generation.

I size TTL and renewal from measured pause and network budgets, but fencing—not clocks—is the final safety boundary. I prefer constraints, compare-and-set, or idempotency when they express the invariant more directly. See [consensus and leader election](/learn/consensus-and-leader-election), [replication and failover](/learn/replication-and-failover), and [idempotency](/learn/idempotency-and-deduplication).”
